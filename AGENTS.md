# Structure
This is a monorepo with multiple microservices.

## Go services (9)
* `run-controller` — owns run lifecycle state (pending → running → finalized, in `runs` and `tasks`, each task keyed by `run_id`; a run's `last_progress_at` marks its latest progress), the crons of its schedules (`schedules`) and a copy of every promoted topology; the authoritative write-path for task and run transitions. Serves gRPC `run.v1.RunService` (port 50051), the one gRPC interface to runs: the commands that start a run (`StartRun`, `TriggerRerun`, `TriggerRebase`, `TriggerSingleNodeRun`) and cancel one (`CancelRun`, `CancelActiveRun`), the schedule commands (`UpsertSchedule`, `DeleteSchedule`, `PreviewSchedule`), and the reads of runs, tasks, attempts, nodes, schedules, the schedule graph and the topology tiles. Every command that starts a run, and `CancelActiveRun`, requires a UUID `request_id` and runs once per tenant and request id: the first call records `(tenant_id, request_id)`, the command, a fingerprint of its parsed parameters and its run in `command_requests` in the transaction that creates or cancels the run, a repeat with the same fingerprint writes nothing and answers with that run (even once the schedule has another active run), the same id with other parameters is `ALREADY_EXISTS`, a call that keeps losing its id to concurrent calls of it that roll back is `ABORTED` (and may be sent again with the same id), a refused call stores nothing, and the retention sweeper keeps a record for at least 30 days (the longer of `RETENTION_DAYS` and the replay horizon); a call that ends `created`, `replayed`, `conflict` (the reused id) or `no_run` (a `CancelActiveRun` of a schedule with no active run) is counted in `continuo_command_requests_total{command,outcome}`, and a call that ends in any other error, `ABORTED` included, is not. A schedule is a schedule name, the first dbt tag of the live release's models (`topology_nodes.schedule_name`); its cron, when it has one, is its row in `schedules` (one per tenant and name: the cron, its IANA timezone, description, paused flag, `next_fire_at`, a `version` only an operator's edit raises, and `updated_by`/`updated_at`), and a new install has none. The schedule commands take no `request_id`: `UpsertSchedule` with an `expected_version` above 0 saves only while the row is at that version (`ABORTED` otherwise), with 0 the last write wins (a save another edit overtook reads the row again and saves over it, up to three tries, then `ABORTED`), the first cron of a name no model of the live release carries is `NOT_FOUND`, a name longer than 50 characters (the longest `runs.schedule_name` stores) is `INVALID_ARGUMENT`, and so is a cron the parser refuses (a `CRON_TZ=` or `TZ=` prefix, an empty, `Local` or unknown zone, a cron that never fires, an `@every` under a minute), with the parser's message; `DeleteSchedule` of a name with no cron succeeds; `PreviewSchedule` writes nothing; maintenance mode refuses `UpsertSchedule` and `DeleteSchedule` with `UNAVAILABLE`, not `PreviewSchedule`. `ListSchedules` lists every name the live release carries or that has a row, with its cron, `model_count`, cron in words and last run; a row whose stored cron does not parse is listed with no cron. A trigger (`StartRun`) refuses a name longer than 50 characters (the width of `runs.schedule_name`) with `INVALID_ARGUMENT` before it reads any schedule or the topology, as `UpsertSchedule` does, then checks the name under the topology lock: a name that no model of the live release carries and that has no row is `NOT_FOUND`, and a row with no models is the empty-selection refusal. Its cron loop fires the schedules of every tenant from their rows: it passes at startup, when the earliest next fire after its last pass comes, on every notification of the `schedules` table's statement trigger and every 60 s; a pass fires up to 100 due schedules, each in a transaction of its own (bounded by 30 s) that locks the schedule row and then the topology and acts under the row's tenant, and fires only the latest due slot, counting and logging the older slots it missed (at most 1000 per fire); `runs.scheduled_for` and `uq_runs_scheduled_for` allow one run per slot, so a slot that already has its run is consumed with nothing written, while an active run of the schedule or maintenance mode consumes the slot with no run; a fire that fails or runs out of time keeps its slot and is counted `failed` once per pass that tries it (a fire ended by shutdown is not), and its schedule is tried again only after a backoff of one minute, counted from the end of the failed fire, that doubles with each failure up to fifteen (an operator's edit or a fire that succeeds ends it; a schedule a pass did not read keeps its history), during which it takes none of the pass's 100 places, a paused row is never due whatever its `next_fire_at` holds, and a row whose stored cron does not parse is skipped and logged. `continuo_cron_fires_total{outcome}` (`started`, `skipped_active`, `skipped_maintenance`, `empty_selection`, `invalid_node_type`, `missed`, `failed`) counts the fires and `continuo_schedules{state}` (`scheduled`, `paused`, `unparsable`: a row whose stored cron or timezone no longer parses, paused or not) the rows, each in one state. Consumes `release.promoted:v2` (group `run-controller-release-promoted`): reads the release's topology artifact from S3 before the transaction, stores the release's nodes and edges once (`topology_releases`, `topology_nodes`, `topology_edges`) and moves its own `live_release` only for a higher `promotion_seq`. Reconciles seeds against `node_materializations` (the version each node last loaded) in that transaction and every 60 s, under one advisory lock, creating one promote-seed run whenever a live seed's `content_hash` differs. A `release.promoted:v2` with `rebaseline` records every live seed of its release as loaded at its new content hash and column fingerprint in the promotion's transaction, so it starts no promote-seed run. A tenant is chosen once, where work enters `run-controller`, and the data carries it from there: the gRPC edge (the tenant the identity interceptor places on the request), a cron fire (the tenant of the schedule's row), and `release.promoted:v2` and `task.status.updated:v2` (the envelope's tenant; a report finds its run by that tenant and its run id, so a report whose envelope names another tenant than its run's is dead-lettered). Every key of `runs`, `tasks`, `task_attempts`, `node_leases` and `schedules` leads with `tenant_id`, a run carries its tenant (a promote-seed run's id includes it), and each `run_controller_outbox` row stores its tenant inside its payload, which the relay renders into the envelope of its `task.dispatch:v1` and `run.cancelled:v1`. Plans every run in the transaction that creates it (`run-controller/service/runstart` over `run-controller/domain/runplan`): stamps it with the release it runs on (`release_id`, `promotion_seq`), chooses its tasks from that release's stored nodes and edges, stores them with their `node_key`, adds attempt 0 of each ready task not left waiting for its node's write lease to `task_attempts` and writes one `task.dispatch:v1` dispatch per such task to its outbox; a manual trigger whose selection cannot make a valid run fails the RPC and creates no run, while a cron fire records the run `failed` (with `failure_reason` `empty_selection` or `invalid_node_type`). A node of type `unknown-external` is stored like any node but is never a task: a whole-schedule run and a rebase read past it, a `TriggerSingleNodeRun` of it or a `TriggerRerun` that would execute it is `INVALID_ARGUMENT`, and `GetScheduleGraph` returns it with an empty `service_name` and the edges to its readers. A stored node type `ingested` (in a topology artifact, a `topology_nodes` row or a catalog `:Node`) reads as `unknown-external`: `model.CanonicalNodeType` converts it at the artifact decode (`pkg/topologyartifact`), in run-controller's reads of its topology rows and in catalog's `GetNode`. A dormant node (a node of a type a release builds, runtime `dbt` or `python` other than `dbt-test`, whose schedule is empty; `model.IsDormant` decides it and nothing stores it) is in no schedule: a cron fire, a `StartRun`, and a rerun or rebase of a schedule's run never include it, except to rebuild a dormant view or materialized view below a seed: any run whose load of that seed drops the seed's table rebuilds it, and a rerun or rebase of that run rebuilds it again if the rebuild did not finish. Otherwise only a run started by hand executes it: a `TriggerSingleNodeRun` runs it, and a `TriggerRerun` of that run runs it again. Consumes `task.status.updated:v2` (group `run-controller-task-status-updated`): in one transaction a report moves its attempt by rank (a lower-ranked report, or one for an attempt that has ended, changes nothing); a success dispatches the tasks it makes ready, a failure whose class is retried (`task`, `resource`, `infra`, `start`) adds the next attempt and dispatches it while the task has budget (`runs.taskMaxRetries`, stamped on each task when its run is created), any other failure (`timeout`, `invalid`, or the budget spent) fails the task and skips the pending tasks below it, and the run finalizes once every task has ended; a report for an attempt it never dispatched is dead-lettered and one for a run that ended is dropped. Every 60 s its attempt reconcile re-sends the dispatch of each attempt it has heard nothing of, with `known_status` (a dispatched attempt after 5 minutes, then at gaps of 10, 20, 40 and 60 minutes and every 60 after that; an acknowledged one after 30 minutes of silence, then every 30), and fails each run left with nothing in flight and no progress for 5 minutes as `stalled`. A writing task (every operation but `test`) takes the write lease on its node (`node_leases`, one per node per tenant) in the transaction that dispatches it, holds it across retries and through `stopping`, and releases it in the transaction that ends the task; a ready task whose node another task of its tenant holds, or another task of its tenant already waits for, stays `pending` with `wait_reason` `node_lease` (since `lease_wait_since`), and its task reads (`ListTasks`, `GetRunGraph` and `ListNodeTasks`) name the run that holds the node (`waiting_on_run_id`, joined from `node_leases` when read). Its background loops (cron loop, attempt reconcile, lease waker, seed reconcile, topology retention, startup settle) read every tenant's rows and act on each row under that row's tenant, the seed reconcile with one pass per tenant's live release. Its lease waker runs a pass at startup, on every `node_leases` notification (the table's trigger sends one when a committed transaction released a lease), every 60 s and before each stall scan of the attempt reconcile: it deletes each lease whose holder task has ended (`continuo_node_leases_repaired_total`), and grants each free node to its oldest waiter whose run is `running` (up to 200 per pass), taking the lease and dispatching attempt 0 in that run's transaction. A lease wait counts as in flight while its node's holder is in flight or an older waiter of a running run waits for the same node, and before the attempt reconcile fails a running run as `stalled` it grants, under the run's lock, each free node a waiting task of the run is next in line for (taking the lease and dispatching attempt 0, as the waker does): a lease wait is never failed `stalled` while its node is held by a task in flight, while it is queued behind an older waiter, or while its node is grantable to it, except that a grant that keeps failing (a defect in run-controller) fails its run once the run has made no progress for 10 minutes, so the node's next waiter is served. A cancel is asynchronous: in one transaction it ends the run's pending tasks, and each task with no open attempt, `cancelled`, moves its tasks whose attempt is open to `stopping` and the run to `cancelling` (a run with nothing in flight ends `cancelled` at once), and writes one `run.cancelled:v1` to its outbox; a `cancelling` run starts nothing, holds its schedule (no cron fire or trigger creates a second run, and a rerun or rebase of it is refused), and a second cancel of it succeeds and changes nothing. A `stopping` task takes the report of its attempt: `stopped` ends it `cancelled`, a success or failure that the container reached first ends it `succeeded` or `failed`, and the run ends `cancelled` after its last task ends. The attempt reconcile re-sends `run.cancelled:v1` naming the attempts still unanswered (the first one 5 minutes after the cancel, then at gaps of 10, 20, 40 and 60 minutes, and every 60 minutes after that), and a run `cancelling` for more than 15 minutes raises `continuo_runs_cancelling_overdue`. At startup it cancels every active run whose tasks it did not plan; serves run graphs, run lists and active-run drift from Postgres (`GetRunGraph`, `ListRuns`, `ListActiveRunDrifts`), each read from the run's own release, and the schedule graph and the topology tiles (`GetScheduleGraph`, `ListScheduleTopologies`) from the nodes and edges of its live release in its own Postgres (`GetScheduleGraph` marks each node `dormant` and gives a dormant node its `last_run_at`, the creation time of the run of its newest run or full_refresh task (a test is no run of it), the last run `ListNodes` reports, read through the index `idx_tasks_node_key_created`, and `ListScheduleTopologies` returns the live release's `dormant_node_count`); `ListNodes` lists every node its live release builds, one that never ran included (with no stats, after the nodes that ran), never an `unknown-external` node, a dbt test or a node the live release does not hold, each row with its `node_type` and `dormant`, and `dormant_only` keeps only the dormant nodes; `ListNodeNames` and `ListNodeServices` name the tables and the services of the nodes `ListNodes` lists; and `ListNodeTasks` carries each task's content hash. A rebase restarts a failed run from its failure on the live release (the failed part, new nodes, everything below them and, when asked, every changed node upstream of those), and `PreviewRebase` reports that selection without creating a run. Every run that loads a seed (every kind but a `test` run) applies `pkg/seedreload` with the warehouse family of `WAREHOUSE_ENGINE` (`postgres`, or empty, is `schema_bound`; `trino` is `late_binding`; any other value stops `run-controller` at boot): a load that drops the seed's table brings the views and materialized views below the seed (walked through `ephemeral` nodes, stopped at any other node), whatever their schedule and a dormant one included, into the same run as rebuild tasks that wait for the seed and for the views they read, a view below two loaded seeds being one task. Each task stores its own `operation` when it differs from the run's, its `plan_reason`, its `seed_preflight` (a dropping load's check: `check` mode on `schema_bound`, `report` on `late_binding`, with the relations the run rebuilds as `allowed` and the objects an operator named as `acknowledged`) and its `rebuild_seed_key`, and every dispatch of the task, a retry, a lease grant and a re-send included, carries them. A load no command can apply is refused at planning (`invalid seed_full_refresh_disabled`): its task fails at attempt 0 and starts no container, the tasks below it are skipped, and a `TriggerSingleNodeRun` of it is `INVALID_ARGUMENT` with no run, as is one with `acknowledged_dependents` that is not a seed's full refresh. A dropping load's success opens, in the transaction that records it, a `view_outages` row (`missing` on `schema_bound`, `stale` on `late_binding`) for every rebuild task of the run the seed reaches, an open row keeping its `since`; the next success of a task at the node closes it, and `ListNodeTasks` returns the node's open outage and, for a task its preflight stopped, the `blocking_objects`. A rerun or a rebase executes again the rebuilds its source did not finish, even when it inherits the seed's load. `continuo_seed_reloads_total{action,outcome}` counts the dropping loads that ended and the loads the planner refused, `continuo_seed_reload_stops_total{reason}` the tasks a seed rule stopped, `continuo_views_missing{state}` the open outages and `continuo_view_outage_seconds` how long each lasted.
* `catalog` — owns the Neo4j graph: the live topology (`:Node`, `:DEPENDS_ON`), the code-version history behind it and the failure-precedent case base. Every node carries a `tenant_id`, which leads every uniqueness constraint and index, and catalog keeps no Postgres. Consumes `release.promoted:v2` on three groups, `catalog-release-topology` (the topology swap, applied only when the promotion's `promotion_seq` is higher than the tenant's live one), `catalog-release-versions` (the code versions; it does not wait for the swap and creates inactive a node the swap has not written yet) and `catalog-release-contracts` (the contract versions and the live contracts folder, described below), `remediation.requested:v3` (`catalog-remediation-requested-rejections`, which records a `:Rejection` only for a node the trigger does not mark `unfixable`, so a trigger whose every node is unfixable writes only its processed-message marker), `remediation.pr_opened:v1` (`catalog-remediation-pr-opened-proposals`) and `remediation.pr_closed:v1` (`catalog-remediation-pr-closed-provenance`). A message's tenant comes from the message (the envelope's for `release.promoted:v2` and `remediation.requested:v3`, the `tenant_id` field agent-remediation stamps on its pull-request events), and a message without one is dead-lettered as permanent. Every code version it stores (the compiled and the raw code, a shared source) and every rejection's error excerpt and code pass through `pkg/sanitize.Text`, which replaces a credential, a private key or an email address with `[redacted:secret]`, `[redacted:key]` or `[redacted:email]`, so neither the graph nor a `catalog.v1.CatalogQuery` read serves one (a version stored before the rule is not rewritten). Each group records a processed-message marker (`:ProcessedMessage`, found by stream message id or by the producer's outbox entry id) in the Neo4j transaction that writes the message's data (the versions group, which writes in batches, in its last batch's; the contracts group in the transaction that follows the live folder's rewrite), and every write transaction first locks the tenant's export lease node (`(:Meta {key:'export'})`): while an export or a restore holds the lease the write backs off like an outage and writes no dead letter. A write that leaves its message unfinished (a non-final batch of the code versions, or the contract versions written before the live folder's rewrite) marks the message in flight on the tenant's lease node, and an export waits until the message's last write, or at most two minutes after its last batch; the contracts group renews its mark through the live rewrite, so an export waits for the rewrite too. A node a release drops stays, retired (`active=false`, `retired_at`), with its versions, failures, fix PRs and `:CURRENT` edge, and loses only its outgoing `:DEPENDS_ON`. A dormant node is stored like any node, with an empty `schedule_name`, and a release that tags it moves the same `:Node` to its schedule. At startup, before any consumer or the gRPC server starts and with readiness false, `InitSchema` migrates the graph to this shape, idempotently. It writes no event and keeps no outbox: `run-controller` reads each release's schedule names from its own copy of the topology. Serves gRPC `catalog.v1.CatalogQuery` (port 50052) for topology and catalog reads (nodes, code versions, precedents and contracts: `GetNodeContract`, whose `include_document` returns the published YAML without `servers`, `ListNodeContractVersions` and `GetNodeContractDiff`) under the request's tenant: `GetNode` finds a retired node only with `include_inactive`, and `GetNodeVersions` lists a retired node's versions with none current; the schedule graph is served by `run-controller`, from its own copy of the topology. Its marker sweeper deletes the markers older than the longer of `RETENTION_DAYS` and the 30-day replay horizon. With `catalog.backup.enabled` it exports each tenant's graph on `catalog.backup.schedule` (UTC) to `tenants/<tenant>/backups/catalog/<UTC time>.jsonl.gz`, streamed under the tenant's export lease, keeps the newest `catalog.backup.keep` and exposes the five `continuo_catalog_export*` series; `catalog-backup`, in its image, takes, lists and restores exports. The contracts group reads the release's contract bundle, verified against the promotion's SHA-256, and records each node's contract versions in one transaction, then rewrites the live folder. An invalid bundle, or one of another tenant or release, is dead-lettered, and a missing one is retried. A promotion older than a node's latest contract promotion stores nothing for that node. A dbt model, seed or snapshot keeps its contract versions like a Python node (`:ContractVersion.family` `dbt`), and the live folder publishes each of them except an ephemeral model (its first schema object's `physicalType` is `ephemeral` and it creates no table), whose versions are kept. The live folder is `tenants/<tenant>/contracts/live/<unique_id>.odcs.yaml` plus `_index.json`: an interim index, listing every file about to be put or deleted at version 0, goes before the writes, and the final one last. The group rewrites it under its own lease `(:Meta {key:'contracts-live'})`, which it does not take while an export or a restore holds the tenant's lease. An `_index.json` it cannot read stops every rewrite and is logged as an error naming the key to delete. A live node's contract is current while its contract watermark (`contract_promotion_seq`) is at or above the live folder's watermark (the `contracts-live` node's `promotion_seq`). With `CONTRACTS_SERVER_HOST` set, each file carries a `servers` entry whose type comes from `WAREHOUSE_ENGINE` and whose schema is the node's declared schema (`:Node.schema_name`, else the schema part of the contract id), read from the promotion's own topology artifact when the rewrite is for a promotion (`handlers.WithDeclaredSchemas`), so it never waits for the topology swap of that promotion, and from the graph when the whole folder is rewritten (a change of settings, the start-up refresh); an artifact that cannot be read as the promotion's (corrupt, or another tenant's or release's) leaves the graph's schemas, and one that is missing fails the rewrite so the message is retried; catalog refuses to start on another engine or on invalid server settings. Each contract version's promotion edge (`:CONTRACT_PROMOTED`) records the ontology its bundle's contracts were resolved against (`ontology_version`, `<release_id>@sha256:<hex>` from the bundle's `ontology` value, absent when the bundle names no ontology release). `ONTOLOGY_BASE_URL` (empty, or an absolute `http` or `https` URL with a host name, no credentials, no query, no fragment and no whitespace or control character, one trailing `/` trimmed; any other value stops the process at boot; catalog does not read `ONTOLOGY_ENABLED`) turns each `continuo-ontology:` link of a contract, of its schema objects and of their top-level columns into `<base>/<rest>` in the live folder and in `GetNodeContract`'s published document, both through `contractversion.Published`; the published `provenance` property gains `ontologyVersion` only when the version has one, and the live folder's settings fingerprint names the base URL only when it is set, so an install that leaves it empty keeps its fingerprint. `CONTRACT_HISTORY_RETENTION_DAYS` above 0 starts a contract-history sweeper that keeps each node's current version and the one before it. It exports `continuo_catalog_contract_versions_written_total`, `continuo_catalog_live_contract_writes_total{op,outcome}` and `continuo_catalog_contracts_duration_seconds{step}`. It calls no `run-controller` RPC.
* `execution-controller` — runs each attempt of a task as one Kubernetes Job. Consumes `task.dispatch:v1` (group `execution-controller-task-dispatch`) and accepts each `(task_id, attempt)` once: a repeated dispatch re-sends the attempt's last report, a Job labelled with the task and attempt is adopted, a dispatch older than an attempt it holds creates nothing, a Job name another task's or attempt's Job holds fails the attempt `invalid job_name_collision`, a Job Kubernetes refuses on every try fails it `infra create_failed` once a live read finds no Job, and an attempt run-controller knows as acknowledged that it holds neither record nor Job for is reported `infra attempt_lost`. Labels each Job with `run-id`, `task-id` and `attempt` (its pods get `TASK_ATTEMPT`), records each attempt in `deployments` under its `run_id` and the tenant of its dispatch, which every `task.status.updated:v2` report of the attempt repeats (a dispatch or cancel whose envelope names no tenant is refused as permanent), sets `activeDeadlineSeconds` to the start timeout plus the dispatch's task timeout, and watches every Job and its pods: an attempt whose pod cannot start (an image it cannot pull, a missing Secret or ConfigMap) has its Job deleted and fails as class `start`, one whose pod starts no container within the start timeout fails `timeout start_timeout`, and one past its deadline fails `timeout deadline_exceeded`. A python task's pod gets `CONTENT_HASH` when its dispatch carries a `content_hash`, and an attempt whose result block names `image_contract_mismatch` fails `invalid image_contract_mismatch`, which run-controller never retries. A seed dispatch with a `seed_preflight` gets a `seed-preflight` init container (`VALIDATION_IMAGE`, `VALIDATION_OP=seed_preflight`, the warehouse Secret), run last before dbt, that lists every object depending on the seed's table: in `check` mode its exit code stops the pod before dbt, failing the attempt `invalid unowned_dependents` when an object outside the `allowed` and `acknowledged` sets reads the seed (or `invalid engine_mismatch` when the validation image's adapter declares another drop family), and in `report` mode it never fails the pod; its findings ride the final report as `seed_preflight`. Once a `report`-mode load succeeds, a one-shot `probe-<job>` Job (`VALIDATION_OP=probe_views`, under 40 s) queries the views outside the allowed set that the preflight found and records each answer in the findings, never failing the attempt. A malformed `seed_preflight`, or one on a node that is not a `dbt-seed`, fails the attempt `invalid malformed_dispatch` before any Job, and a `full_refresh` whose dbt-commands block defines no command for it fails `invalid seed_full_refresh_undefined` or `invalid full_refresh_undefined` only once neither the Job watch's cache nor a live read shows a Job or an unfinished pod of the attempt (a Job made while the block defined the command is adopted first, and an unfinished pod waited for); an attempt run-controller knows as acknowledged with nothing of it alive is reported `infra attempt_lost` instead. The seed-build leg's pod runs the same init container, always in `report` mode, and returns its findings on `seed.build.completed:v1`. Uploads logs and results to S3 and reports each production attempt on `task.status.updated:v2` (`queued` once accepted, `running` once its main container starts, then the final report with its failure class and reason once no pod of it can run again); it never retries a task, since run-controller decides. Consumes `run.cancelled:v1` (group `execution-controller-run-cancelled`): it records the run in `cancelled_runs` (kept for the 30-day replay horizon), and every gate where work starts checks that fence — a dispatch of a fenced run creates no Job and is answered `stopped`, a row waiting for a slot ends `stopped`, a launch re-checks it under the row lock — then deletes the Jobs of the run's started attempts, and of a row waiting for a slot whose Job a launch created and lost before its commit (the row adopts the Job and waits for its pods), reaps a fenced run's Jobs it holds no record of and a Job created after its create call reported failure, and reports each attempt `stopped` once no pod of it can run again, or with the failure it reached when its container failed before the stop was requested. A warehouse statement a pod sent may outlive the pod: `stopped` means no pod can run again, not that the warehouse has stopped. A fix verification run's compile and seed-build Jobs lay the run's source overlay over a staged copy of the project (the `overlay` initContainer of the s3-sidecar image) and then remove each path the overlay's reserved `.continuo/delete-paths` member lists, which the fetcher validates and writes to `OVERLAY_DELETE_LIST` (`/shared/overlay-delete-paths`); a listed path that cannot be removed stops the container. Release legs (validation, seed-build, compile) surface their outcome into the release lifecycle.
* `release-controller` — manages blue/green candidate-release lifecycle; tracks the `current_prod` pointer and drives promotion/rejection. A node of type `unknown-external` is never changed, built, validated or cloned, so the changed set, the build and validation sets and the duplicate-table check leave it out, and the `service_prod` coverage check at activation skips it because it has no service. A dormant node is validated like any model: built from its own code when it changed or sits below a node that changed, and copied from its production table (`clone_from_prod`) when it is only an upstream of those, like any node. When every node that failed validation is such a copy, the release is rejected `upstream_clone_failed` (not healable) with the detail `Could not copy the production table of <ids>. Run <it|them>, then release again.`, where `<ids>` names up to five nodes in id order and counts the rest (`a, b, c, d, e and 7 more`); when a node built from the release's code failed too, the reason stays `validation_failed`, `failing_nodes` leaves the copies out, and the detail ends with that sentence. Each `per_node[]` entry of a validation rejection names its `validation_op` (`build_from_sql`, `build_from_columns`, `check_binds` or `clone_from_prod`, the contract's `validation_op` vocabulary). Besides its internal HTTP API (8088) it serves gRPC `release.v1.ReleaseQuery` (port 50056, `RELEASE_CONTROLLER_GRPC_PORT`): `GetReleaseNotices`, read-only, a candidate release's seed reload notices, which `continuo release notices` reads (the chart's NetworkPolicy admits agent-chat alone to the port); a failure of that server stops the process. For each changed seed production holds whose load drops its table or is refused, it stores a notice on the release (`release_pipeline_runs.notices`, built with `pkg/seedreload` and the family of `WAREHOUSE_ENGINE`, an unsupported engine stopping it at boot): what the load does and why, the views the promote-seed run rebuilds (a dormant one included), the nodes that refresh only on their own schedule (a dormant one, whose schedule is empty, only when run by hand), and a prediction (`reloads`, `stops` or `refused`). The seed-build leg carries a `report`-mode preflight for each such seed that is not refused, whose findings name the objects outside continuo that read it and, on `schema_bound`, predict `stops`. A notice never rejects a release, and a verification run or a rebaseline release gets none. It accepts the kinds `dbt` and `python-odcs`, on a release and on a verification run, and `ontology` on a release only, and answers one that names the kind `python` with HTTP 400 (`kind "python" is no longer accepted: release the service as "python-odcs", one ODCS contract per node (docs/contracts.md)`); a run stored with the kind `python` still loads, and one still queued or in flight is rejected `invalid_artifact` with that refusal as its detail (a verification fails, with no release event) at activation or at the next result of its parse, seed-build or validation leg, so it never promotes or writes `service_prod`, and a verification of a release stored with that kind is assembled from production. The kind `ontology` is the install's company ontology (`ONTOLOGY_ENABLED`, read at boot: `true` or `false`, unset or empty is `false`, any other value stops the process): a release of it is answered 400 while the switch is off (`kind "ontology" is accepted only when the install's ontology switch is on (contracts.ontology.enabled)`), a verification run of that kind 400 (`a verification run cannot have kind "ontology"`), a release of it for a service while another service has the kind `ontology`, in `service_prod` or in a candidate run that has not ended, 409 (`service "<other>" is the install's ontology: an install has one ontology service`), and so is one for a service whose `service_prod` row has another kind, or another kind for the service whose row has `ontology` (`service "<name>" is released as kind "<stored>": a service cannot change between kind "ontology" and a node kind`); an ontology submission takes the release-queue lock before it loads the run, and the rules apply only to a submission that would create a run, so a resubmit of a stored release id stays idempotent. A run queued before another run of its service promoted meets the same kind-change rule when it is activated, under the queue lock and with the `service_prod` pointers it reads: a run whose kind is on the other side of that line from its service's pointer ends rejected `invalid_artifact` (a verification fails, with no release event) with the same sentence as its detail, promotes nothing, writes no `service_prod` row, and the queue goes on to the run behind it. A run of the kind `ontology` that is queued or parsing when the switch is turned off ends rejected `invalid_artifact` the same way, with the 400's sentence as its detail, at its activation (before the pointers are read) or at its parse result (whatever the result), since topology-controller ignores the ontology file with the switch off and promoting the run would store a file nobody read as production's ontology. An ontology release has no compile leg (`HasCompileLeg` is true for `dbt` alone), goes from `received` straight to parsing, has no node to validate, promotes by the nothing-to-validate path and writes a `service_prod` row of kind `ontology` (release migration `V32` makes both `manifest_kind` CHECK constraints accept it), and every other release carries that row's pointer in its manifest set, so each release reads the production ontology. Release migration `V30` raises `these services are still released as kind "python": <names>` while a `service_prod` row has that kind, which stops the `db-init-migrate` hook Job and so the upgrade on an install with its own database, and at startup, before anything but the health routes serves, it runs the same check and exits after logging the names, which covers the bundled Postgres, where the migration Job is no hook. It stores a parse's contract bundle reference and `continuo_contracts` on the release, carries the bundle's URI and SHA-256 on `release.promoted:v2`, and returns them on its internal `GET /releases/{id}` (the public release status names only `continuo_contracts`). It also stores a parse's `parse_ms`, `contracts_ms` and `contracts_by_family` (release migration V31: three nullable columns of `release_pipeline_runs`; `release.NewParseTimings` leaves both durations NULL when both decode as 0 and the count NULL when it decodes as nil, so a result of an older topology-controller sets none) and returns each on the same internal `GET /releases/{id}` and on `GET /verification-runs/{id}`, only when set. It deletes `contracts.json.gz` with the topology artifact of a pruned release that was not promoted.
* `remediation` — failure classifier; triages a rejected release's failing nodes one by one, records every decision, and emits ONE `remediation.requested:v3` heal trigger per (release, remediation round) carrying every failing node it newly recorded: a node it drops, which no change to the release's source fixes, is carried marked `unfixable` with the reason `classifier_infra` (an infrastructure rule matched) or `classifier_unhealable_parse` (a parse failure of a kind not healable) and what actually failed as its detail: the failure's key error line (cleaned of credentials and email addresses with `pkg/sanitize.Text`, then capped at 4 KiB, the parser's detail for a parse node), or the matched rule when there is no line. The matched rule stays in the node's `reason` and in its `classification_decision`. The trigger is enveloped, its `source` a value of the `remediation_source` vocabulary, and stored under the tenant of the message it answers: a `release.rejected:v1`'s `tenant_id` field (the default tenant when it names none), or the envelope's tenant of a `remediation.retry_requested:v2`, the enveloped "Try again" of release-controller that carries the release's stored rejection unchanged as `rejection` and the next round (one that names no tenant is dead-lettered as permanent). It drops a rejection whose reason the `reject_reason` vocabulary marks not healable (`upstream_clone_failed` among them) before it reads a node, recording no decision, and never turns a validation entry whose `validation_op` is `clone_from_prod` into a failure to fix. It counts each failing node's decision once, when it records it, in `continuo_remediation_classified_total{decision,reason}` (`decision` `emit` or `drop`, `reason` the family of the rule that matched: `infra`, `parse`, `logic`, `test` or `unknown`).
* `agent-remediation` — LLM fix-proposer; works a whole rejected release at a time. Receives one batched heal trigger (`remediation.requested:v3`), groups the failing set (same error signature + a shared changed ancestor become one cluster fixed at that ancestor), calls the LLM once per cluster (once per pre-flight round of each), and reads source from GitHub (read-only) for compile/seed_build/duplicate_table failures and primarily from the release's code bundle in S3 for validation failures (falling back to GitHub only on a permanent bundle miss), leaving out of the context a repository file over the reader's 1 MiB cap and declining the cluster when that file is the one to fix; also reads narrow graph context (source location, upstream diffs, current version, failure precedent) from catalog. Every fix is verified by a real verification run per edited service before it is offered, and one attempt yields one proposal and one fix PR for human approval. Every heal trigger is worked by the runner: it keeps the nodes the trigger marks `unfixable`, records the envelope's tenant on the remediation (the default tenant when it names none) and stores every outbox row it writes (`remediation.proposed:v1`, `remediation.handed_over:v1`, `consumer.dead_letter:v1`) under it. At every start, before the runner's worker and the `remediation.requested:v3` consumer run, it fails every attempt row in `generating` or `verifying` that has no remediation id (a row nothing drives, since the runner stamps a remediation on every row it writes) with the reason `continuo changed its remediation engine while this attempt was in flight; use Try again` (a `generating` row takes it as its rationale, a `verifying` row as its `verify_error`, and each node outcome still in flight becomes `failed` with it), so the release page offers Try again, which starts a new round. The chart rolls agent-remediation with strategy `Recreate`, so a pod of the previous release has stopped before this step runs and cannot write such a row after it. The runner records each trigger as a `remediation` (one per tenant, release and round: `running`, `done`, `system_failure`) in four tables, `remediation`, `remediation_try` (`drafting`, `checking`, `verifying`, `passed`, `failed`), `remediation_cluster` (`gathering`, `proposing`, `preflight`, `checked`, `handed_over`, `fell_back`) and `remediation_step`, the journal of every step run (`running`, `waiting`, `done`, `failed`) with its input digest, output, findings, model, tokens and failure count, and stamps `proposal.remediation_id` on every proposal row it writes. A worker claims the oldest running remediation by lease (`FOR UPDATE SKIP LOCKED`, five minutes, renewed every third) and drives it one step per transaction: the step's row and what it changes commit together after the lease is held, no transaction stays open across a model call, and the model's idempotency key and the gate's run ids are derived from the remediation, try and attempt, so a restart continues from the last committed step and a repeated call costs nothing. A cluster runs its context steps only while it is `gathering`, and a step reads back the rows of the steps already run, never the loaded files' lists of them: a cluster's evidence is rebuilt from its first round's done context rows, a round after the first is given the round before it from that round's prompt and pre-flight rows, a cluster in `preflight` runs its pass on the draft of its round's done prompt row, and the cross-cluster checks and the gate rebuild each checked cluster from its done check and pre-flight rows; a new round's prompt step and pre-flight checks run as the loaded files list them for the cluster's type, so a try open when the files change (a deploy, an install's edit) finishes on the context steps it ran, and a row's evidence of a key no registered step provides is left out and logged. The gate poller claims each verifying remediation by the same lease and renews it the same way while it polls; a lease another process took stops the drive or the poll at once, with nothing written. A step stopped after ten minutes or failing counts a failure on its row, and a remediation that cannot be loaded or cannot open its next try counts one on its own row (`failures`, `last_error`, cleared when a try opens or when a step commits after a load that found a try open); a remediation with a step failed five times, five failures of its own in a row, or a drafting or checking try past its deadline ends `system_failure` (a verifying try waits on the gate's own timeouts), checked by the runner before every step, before a try opens and before every gate poll, by the worker after a drive that fails, and every minute by the sweeper; a drive that fails and is not stuck parks the remediation for two minutes. A system failure leaves the try in its status, fails its attempt row with a reason that names the dead letter, and in the same transaction dead-letters the heal trigger on `consumer.dead_letter:v1`, with the fields and payload it arrived with, so a redrive republishes it; nothing claims, polls or sweeps a remediation that is not `running`. A redriven trigger whose remediation is a `system_failure` resumes it in one transaction: the remediation runs again with its failures cleared, the open try's unfinished steps lose their failures, a drafting or checking try gets its full time again and its attempt row goes back to `generating` or `verifying`, so no second remediation is made and no committed step runs again; a redrive of a round a later round replaced, or of a remediation that runs or is done, resumes nothing. The retention sweeper deletes a `system_failure` remediation like a `done` one, past the longer of `RETENTION_DAYS` and the 30-day replay horizon, and a redrive after that starts the round afresh. Flows and types are YAML files built in from `agent-remediation/workflows/`, each with a `kind` (`flow`, `type`, `fixture`); the one flow, `rejected-release`, lists ten types (each matching a cluster shape, source and node types, and giving its `rounds`, 3 for every built-in type), the context steps every cluster runs first (`previous_tries`), the cross-cluster checks, the gate, the `pull_request` and `hand_over` outputs and `tries`. The `duplicate-table` type moves the model a release added, in the same schema, to the next free `<name>_v2` (`_v3` when `_v2` is taken, in the model's project or, through catalog's `GetNode`, by a node of any service; a model's name is its file's name in dbt): its context step `model_rename` reads the model's project from a checkout (`ports.ModelReferenceFinder`), picks the name and gathers every file that names the model (its `models:` properties entry, each `ref('<name>')` or `dbt.ref('<name>')` of a SQL or Python model or a properties file's test, a two-argument ref only when it names the project's own package, and `dbt_project.yml` when its `models` tree holds a key of that name), its prompt has the model return the file at its new path and those files renamed, and its pre-flight check `rename_matches_plan` refuses a draft that does not move the file to the planned path, edits another file, or leaves a file naming the old model (the files the draft moves away left out). When the model's alias, not its name, makes it write the table in dispute, the alias changes to the next free name instead and no file moves. The edit that moves the file carries `RenamedFrom` (gRPC `FileEdit.renamed_from`), its stored diff is a rename diff, and the verification overlay lists the old path in its reserved `.continuo/delete-paths` member, so the run builds the project without it. A model whose properties declare neither `continuo.entity` nor `continuo.grain`, in a project whose other models declare one, is declined before any model call (`Renaming it to <name>_v2 fixes the duplicate, but the model has no metadata: add continuo.entity or continuo.grain to its schema.yml entry.`), since what a table is is its owner's to say, and a cluster that finished gathering before its type listed `model_rename` is declined with `use Try again` (its check refuses `rename_not_planned`). The pull request's rationale opens with which node already builds the relation and that the owner may choose another name. An install's own flow, type and fixture files in `AGENT_REMEDIATION_WORKFLOWS_DIR` (default `/etc/continuo-workflows`, filled from the chart's `agentRemediation.workflows.files`) load over them at startup: a file with a built-in's `kind` and `name` replaces it whole and startup logs the replacement at Warn, a `based_on: <name>@<revision>` warns when that built-in has moved since, a flow other than `rejected-release` is warned about (`flow <name>: no heal trigger runs it`), and `remediation-check files <dir>|steps|--help` ships in the image. Startup loads every file and checks it against the step registry, and refuses a bad file naming file and line (a gate is exactly one step, a type's `rounds` is at least 1, a flow names an `approver` step and a `model_may_see` list of known data classes, and a context step the flow or a listed type runs, or a prompt a listed type uses, never provides or reads a key of a class that list leaves out), and files without `rejected-release`, the flow every trigger runs; that flow's `tries` is how many attempts a release round gets. Steps are Go types under `service/steps`, reached only through `service/runner/registry.go`, and a cluster runs them in the order flow context, type context, prompt, pre-flight, the context steps once per try (in its first round) and the prompt and pre-flight once per round; the try's drafts then pass the cross-cluster checks and the gate, and the output ends it. A draft that pre-flight refuses goes back to the model in the same try while the cluster has rounds left, up to its type's `rounds`: the next round is one new single-shot request (the LLM port has no revise call) made of the round's last request, the model's last answer and every finding of that round's pre-flight pass, with its own model call and idempotency key; the prompt row's journal output stores the round's last request and answer, so a restart revises the same call. A cluster whose last round is refused is handed over `failed` with the code `preflight_rounds_spent` and the first finding as its reason, and an upstream cluster then falls back by the fixed rule (each member of a shared-upstream cluster becomes a cluster of its own, the members of a cross-service cluster are skipped with the cause's code, `declined` or `preflight_rounds_spent`). The model's refusals are findings, not declines: an empty or unchanged answer, a low-confidence one, a file it was not shown and a contract the packager refuses are findings of the type's pre-flight checks (`content_changed`, `confidence_not_low`, `target_file_was_shown` and `contract_packages` among them), so a revision can correct them, while only a context step declines, for a node no fix can reach; a read error that a retry may clear (catalog, repository, object storage) is the step's error, which the runner retries, never a decline, except in the catalog context steps that only add reference (`current_contract`, `upstream_changes`, `failure_precedents`), which log a warning and carry on without it. A cross-cluster check that finds something, or a gate that refuses the drafts at submit, fails the attempt and the try and starts the next try, with the findings among the earlier tries it is shown (the failing set is handed over once the `tries` are spent). A failed verification run names, for the next try, every node release-controller lists in its `failing_nodes` (with the run's `fail_reason — fail_detail` unless the node's own validation or parse result carries a text), and a failure that names no node records the run's own reason and detail (`verification run <id> failed: <reason — detail>`). Every node the runner leaves to a human carries a `handover_reason` code on its outcome (`proposal.node_outcomes[].code`, `remediation_cluster.outcome`, gRPC `NodeOutcome.code`) beside its message: `classifier_infra` or `classifier_unhealable_parse` on a node the trigger marks unfixable (`skipped`, the failure's key error line as message, no model call), `no_type` on a cluster no type matches or a dbt test, `declined` when a step declines (one that gives no reason reads `step <name> declined the fix`) or a draft passes pre-flight with no edit, `preflight_rounds_spent`, `no_repository` when the trigger names none, `unverifiable_edits` on each drafted member of a try a cross-cluster check or the gate's submit refused, and, on the `escalated` row the runner writes once the `tries` are spent, `tries_spent` or `unverifiable_edits` with the message `tried <n> times; the last try failed: <why>` (`tried 1 time` when n is 1) (a node handed over with `declined`, `no_type`, a classifier code or `preflight_rounds_spent` keeps its outcome). A node settled with `declined`, `no_type` or a classifier code is carried into every later try as a cluster already handed over and never grouped again, while a `preflight_rounds_spent` node is grouped again, and a trigger whose every node is unfixable gives one `skipped` attempt row. At every end with a coded node, in the transaction that ends the remediation, the runner runs the flow's `on_give_up` output, `hand_over`, which writes one `remediation.handed_over:v1` (its id derived from the remediation, so it is written once) naming each such node with its code, its message and its owner (`owner`, left out when the node has none); a maintenance-mode end hands over only the unfixable nodes. The runner cleans the message of every coded outcome with `pkg/sanitize.Text` where it records it (every proposal row it writes, and the event), so a credential or an email address in an error line reads `[redacted:secret]` or `[redacted:email]` on the release page and on `remediation.handed_over:v1`; an owner is stored and announced as read. An attempt row's `verify_error`, the error of each verification run on it and the reason a remediation ends as a system failure are cleaned the same way (`proposal.CleanedReason`), so the Remediation tab and the `Proposal` read show the markers. `previous_tries`, the flow's context step, lists the earlier tries at a cluster's member nodes in the release: the runner's tries made before the cluster's own, in its remediation round and the rounds before it (read from their journals through `ListTriesOfRelease`, which returns only a try's done pre-flight rows and done flow-level check rows) and the attempt rows that have no remediation id, except a row the startup sweep failed, which no gate judged. Every first-round request of a prompt step carries the last 3 of them, when there are any, oldest first, each with its diffs, how each of its clusters ended (status, code and reason), what pre-flight and the cross-cluster checks found and why its gate failed, every text cleaned like the rest of the model's input and each diff cut at 8192 bytes, and a revision, built on that request, carries them already. Every evidence key has a data class declared beside its Go type in the registry (`code`: sources, diffs, contracts and drafts; `logs`: the failure text, dbt logs, precedents and earlier tries; `rows`: warehouse rows, which no key holds), and the flow's `model_may_see` (`[code, logs]` in `rejected-release`) lists the classes a model may be shown. The runner is the only code that cleans model input, and steps never clean model input (the change-diff step runs `sanitize.Text` over the two texts it compares, the candidate's and catalog's stored, redacted code, so catalog's redaction never shows as a change, and its diff is cleaned by the runner like any other evidence): the runner passes every string of a cluster's evidence, and on a revision the findings of the rounds before, through a numbering `sanitize.Redactor` that it rebuilds from the journal in the same order for each round of a cluster (so a placeholder means one value across steps and restarts), which replaces a credential, a private key or an email address with `[redacted:secret:<n>]`, `[redacted:key:<n>]` or `[redacted:email:<n>]` (one number per value), so no model request holds one. It writes each edit the way its original is written, CRLF or LF line endings and the final newline (`remediation.KeepFileConventions`), so a fix and its diff change only the lines the fix changes, and it restores the model's draft before pre-flight: a placeholder in an edit's path or content, or in the rationale, becomes its value only when that value occurs, as a whole token, in the edit's original or in code-class evidence the cluster was shown, so a value only a log held never reaches a file or a pull request. A placeholder the Redactor never issued, one that a log or a finding alone held in a path or a file, and a redaction marker an edit adds where its original had none are `unknown_placeholder` findings of the pre-flight pass, which the next round is shown cleaned. The flow's `approver` step, `node_owner`, names each node's owner as its reviewer, in the transaction that ends the remediation, reading the release's code bundle once per call: a dbt node's `meta.owner`, a python node's ODCS `team.name` (the bundle's `owner`), else `team.name` of the `contract_file` evidence of the cluster that worked the node (for a node carried as settled into a later try, the earlier try's cluster that settled it, read back from that try's journal), else no owner (`source` `bundle`, `contract_file` or `none`); a bundle it cannot read is logged as a warning and read as naming no owner, so it never fails the end. The runner stores these approvers (`approvers`, `{node_id, owner, source}`) on the attempt's proposal row for every node it settles at the end, fixed or handed over, `RemediationProposals` returns them on `Proposal` and, for the claim's nodes, on `BeginPullRequestResponse`, and a row with no remediation id has none. The runner counts what it does in `continuo_remediation_tries_total{flow,type,result}` (each cluster a try worked, at the try's end), `continuo_remediation_rounds_total{flow,type,result}` (each pre-flight pass: `passed`, `revised`, `spent`), `continuo_remediation_outcomes_total{flow,type,outcome,reason}` (each node once, when its remediation ends: `fixed`, or `handed_over` with its code as `reason`), `continuo_remediation_system_failures_total{flow,reason}` (each stop: `step_failures`, `remediation_failures` or `deadline`, counted again if a redrive stops again), `continuo_remediation_stage_seconds{flow,type,stage}` and `continuo_remediation_model_tokens_total{flow,type,direction}`, where `type` is a loaded type file's name, or `none` for a node no type matched, and every sample is counted once its transaction commits (a token when a model call that was not a cache answer returns). `service/conformance` plays every listed type (eight scenarios, among them a refused draft the next round passes, rounds spent, and a try that learns from the last one's gate error, each derived from the type's `rounds` and the `tries` of the flow the scenario's remediation follows, `rejected-release` when it lists the type, else the first flow by name that lists it, so a type of one round expects its refused draft handed over) and flow (among them an unfixable node and maintenance mode, each scenario's remediation following the flow it plays, through the runner's `Deps.Flow`, which is empty, so `rejected-release`, in the service), checking the code each hand-over carries, through scripted scenarios over `adapters/memory` (`Suite.Mutate` plants a value into a copy of each fixture and `Result.Requests` returns the model requests of each scenario, so a test holds that no request shows the value and every checked edit holds it again), and `remediation-check files <dir>`, shipped in the image, runs it and prints one JSON report. A Python or csv node's contract is its ODCS file under `contracts/`, found by `id`. A node that no `contracts/*.odcs.yaml` file of the service's repository declares is refused (the runner's `contract_file` step declines). A fix is packed with `continuo-runtime pack` (runtime 0.14.0 in its image) using the image's package list, and verified as kind `python-odcs` from `<service>/<run id>/odcs-bundle.json`. The list comes from the rejected release's contract bundle (`provenance.<service>.image_packages`, named by release-controller's internal `GET /releases/{id}`), or, only for a release that has none, from `<service>/<release_id>/odcs-bundle.json`. With neither, no verification starts and the runner's `image_packages` context step declines the cluster. The gate submits a Python verification run only as kind `python-odcs`: a packaged contract in the try's drafts that is not an ODCS producer bundle (a JSON object with `bundle_version`) is refused at submit with the finding `packaged_contract_not_a_bundle`, like any other refusal of the drafts. The `current_contract` context step shows the model the node's contract from catalog's `GetNodeContract`.
* `agent-chat` — chat and agent gRPC backend; hosts the conversational LLM interface used by the UI. It runs the `continuo` CLI for each approved tool call, giving a mutating call a stable request id (a UUIDv5 of the thread and the call) through `CONTINUO_REQUEST_ID`, so a call run twice starts one run. A tool's parameters are its command's positionals and only the flags the command marks for the chat (`node full-refresh`'s repeatable `--acknowledge`, a list); the chat sets no other flag, and any value beginning with `-`, or a chat-flag value holding whitespace or a control character, is refused. The objects to acknowledge are the `blocking_objects` that `continuo node history` lists on a seed task stopped with `unowned_dependents`.
* `dead-letter-controller` — stores every dead letter from both dead-letter streams (`consumer.dead_letter:v1`, `outbox.dead_letter:v1`) in its own `continuo_dead_letter` Postgres database, serves gRPC `DeadLetterService` (list, get, redrive) for `continuo dlq`, and redrives a dead letter to the consumer group that failed it.
* `egress-proxy` — forward proxy for the outbound traffic of agent-chat and agent-remediation: docker-compose and the Helm chart (`egress.enabled`; the chart only while its allowlist is not empty) point both at it through `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`, and the chart's egress NetworkPolicies drop every other outbound connection of the two. Admits a `CONNECT` tunnel or an absolute-form plain-HTTP request only to a host and port on its allowlist (a YAML file the chart renders from `llm.*`, agent-remediation's `GITHUB_BASE_URL`, `s3.endpointUrl` and `egress.*`), resolves the name itself, and connects only to the addresses it checked: loopback, unspecified, link-local and cloud-metadata addresses are always refused, and a private address is refused unless the entry sets `allowPrivate`. Counts every decision in `continuo_egress_requests_total`.

## Python service (1)
* `topology-controller` — Python 3.14/uv service (not Go); consumes `release.requested:v1` Redis Stream events, batch-loads the release's dbt manifest.json files, resolves cross-service upstream deps via sqlglot, writes the resolved candidate topology once per release to S3 as an immutable gzipped artifact (`tenants/default/topologies/<release_id>/topology.json.gz`), and announces its URI and SHA-256 on `manifest.loaded.candidate:v2` for release-controller (which promotes it by reference — the same artifact's URI, SHA-256 and a per-install `promotion_seq` — on `release.promoted:v2`, and catalog applies a promotion to its Neo4j topology only when its `promotion_seq` is higher than the live one). Every table that a node (a dbt test aside) reads and no node builds, other than a system relation of the install's warehouse engine, becomes one node of type `unknown-external` (runtime `external`, key `schema.table`, no service, schedule, hash or image) that the readers' upstreams name, with no candidate object and no code-bundle entry. A dbt model or snapshot of the service's own dbt project with an owner and no tag is a dormant node: a node like any other with an empty schedule, which runs by hand, and in any run whose load of a seed drops the seed's table only as the rebuild of a view or materialized view below that seed; `is_dormant` (`domain/dormant.py`) is the Python twin of `model.IsDormant`, and a shared fixture pins the two. A dbt node with no owner, tagged `local_stub`, or with no tag and of an installed dbt package is left out (`continuo_topology_release_skipped_nodes{reason}`: `no_owner`, `local_stub`, `installed_package`). The project is the manifest's `metadata.project_name`, else the service the release declares, and a node of an installed package with an owner and a tag (and no `local_stub` tag) stays a node of the package's service, so the service check fails the release `invalid_artifact`. An untagged seed of the project takes the schedule `seed`, and a python node without an owner or a schedule fails the release. A dormant model's table counts as built, so it never becomes an `unknown-external` node, while the table of a left-out model does when a node reads it. `continuo_topology_release_dormant_nodes{service}` counts the dormant nodes of the last release that ended (`service` is the process, as on every series). It also reads a Python service's release, kind `python-odcs` (the `odcs-bundle.json` its CI writes with `continuo-runtime pack` to `<service>/<release_id>/odcs-bundle.json`, one ODCS contract per node); a manifest of any other kind than `dbt`, `python-odcs` or `ontology` fails the release `invalid_artifact`. Each Python contract is read strictly and checked with the `continuo-contracts` version pinned in `pyproject.toml` (0.4.1). A bundle written by a newer library, or two contracts of one bundle with one `id`, is `invalid_artifact`. Every invalid contract is named on one `publish_failed` of kind `invalid_contract` (not healable). Every dbt model, seed and snapshot a release keeps gets its ODCS contract from `dbt.generate` of the same library, inside the dbt parse (stage `contract_generation`, then `contract_validation`), from the node and its tests; a dbt test and an `unknown-external` table have none. The topology's table, relation, service, kind, schedule, criticality, owner, file, materialization and task timeout come from that contract, while its schema keeps the spelling the project declares (the warehouse relation's) and the SQL, config, hashes and edges come from the manifest and the SQL. A contract's id is the node's unique_id, in lower case (`analytics.orders` for a schema declared `Analytics`), and an empty `meta.timeout_minutes` or `meta.criticality` reads as no timeout and `SECONDARY`. A dbt contract the library cannot generate or that fails its checks (a `meta.criticality` other than `REGULATORY`, `CORE` or `SECONDARY`, a first tag over 50 characters or with whitespace, a `meta.timeout_minutes` outside 1 to 10,080, a schema with whitespace, a dot or a slash, a node field of the wrong shape, a manifest entry with no `config.materialized` or `original_file_path`, a snapshot with `contract.enforced`, which dbt does not support, a binding key of the wrong shape in `meta.continuo` (the library shape-checks it whatever the ontology switch says), a table the compiled SQL names or a read the node declares that cannot be listed as `<schema>.<table>`) is named in the same `invalid_contract` rejection, each as one failed node, and so is a seed whose declared columns and CSV header (from the compile extras) differ, by exact name in either direction and in any order; a seed the extras do not name has no known header and is not compared (the parse lists it in `ParsedArtifact.unchecked_seeds` and the handler logs one warning per release with the count). A dbt `relationships` test with an `attached_node` (dbt's own macro, not a project's macro of that name) whose `depends_on.nodes` names an id the manifest holds neither as a node nor as a source (a `local_stub` model the baseline uploader `dbt/dbt_upload` drops) is given to `dbt.generate` as a copy without that id, so its contract carries a `custom` rule keeping `to` and `field` (the library's rule for a target the manifest does not hold), and any other test is given as the manifest holds it; the manifest itself is not changed, and the handler logs one warning per release with the count (`ParsedArtifact.relationship_tests_without_target`). A malformed manifest (`metadata.project_name`, tests, a kept node or test with no `fqn`, a node that is not an object, a `compiled_code`, `raw_code` or `database` that is not text, a `depends_on` that is not an object, a `nodes` that is null, a macro, function or unit test entry that is not an object, text UTF-8 cannot encode) is `invalid_artifact`, and a defect of the library is `internal`. A contract whose `id` is not the unique_id of the node it declares (a non-ASCII capital, which the library accepts) is invalid too, named with the file and both ids. So is a dbt contract whose `id` (the library lowers `<schema>.<table>` as one string) is not its node's unique_id (`relation_key` lowers the declared schema and the table each on its own), which can happen for a capital `Σ`, and the parse compares the two and rejects a difference as one `invalid_contract` failed node naming both ids, counted `validate`/`identity`. Two nodes that declare one unique_id, in one service or two, publish `ok` with neither contract in the bundle (logged), so release-controller rejects the release `duplicate_table`, naming both. Every release that publishes `ok` writes a contract bundle `tenants/<tenant>/topologies/<release_id>/contracts.json.gz` once, after the code bundle and before the topology artifact. It is gzipped canonical JSON holding each contract's stored form (a dbt node's and a `python-odcs` node's, `summary.by_family` counting both) and `contract_hash`, with the tables its SQL or read queries name (a dbt contract also its declared reads). The writer streams it, each top-level value and each contract entry through `canonical_json` into a level-9 gzip compressor, to the very bytes `gzip.compress(canonical_json(document), mtime=0)` gives, and `store_contracts` drops each node's producer document once its stored form exists; `topology-controller/bench/README.md` gives the peak resident memory of the benchmark process on a cold release of 10,000 dbt models of 40 columns, which holds about 80 MiB of in-memory S3 objects that a pod keeps on disk. The bundle is created with a conditional write (`If-None-Match: *`): a redelivered release, or a parse of it another replica runs at the same time, keeps the stored bytes and reports their SHA-256 and their `summary.by_family` (read from the end of the stored JSON the writer already fetched; a stored bundle it cannot read fails the release `internal`). `manifest.loaded.candidate:v2` carries `contract_bundle_uri` and `contract_bundle_sha256` on `ok`, `continuo_contracts`, `parse_ms` and `contracts_ms` (the milliseconds of the parse without its contract stages, and of the contract stages) on both outcomes, and `contracts_by_family` (`{"dbt": n, "python": n}`, a family with none left out: the stored bundle's `summary.by_family`) on `ok`. A manifest of kind `ontology` (`<service>/<release_id>/ontology.yaml`) is the install's company ontology: it declares no node and never reaches the parse loop. `ONTOLOGY_ENABLED` (`true` or `false`; unset or empty is `false`, any other value stops the process at boot) switches it on. With the switch on, the `ontology` stage reads the file once, before any manifest (`ontology.load`, then the library's own `ontology` rule): a file that is not UTF-8 text, does not load, has an error of its own or sits under a key that names no release id is `invalid_artifact`, naming the ontology service. Each contract is stored in the form `bind_contract` gives it: `ontology.resolve` for a contract of a service the ontology declares (its domain, its `continuo-ontology:` links and what the ontology knows of each bound column), as written when no ontology is released, and `ontology.strip` with the switch off, so a contract that writes bindings hashes as one that writes none. Once every node has resolved and every contract is stored (never for a release with a failed node), `ontology_check.check` runs the library's release rules over the whole release and calls `progress` after each contract: an error that names a contract is one failed node of kind `invalid_contract` (`ontology <rule>: <message>`, the errors of a node joined), one that names none is `invalid_artifact` naming the ontology service, and a warning or an information finding never rejects: it goes to the bundle's `ontology.findings`, and its counts to the release's log line (`ontology_warnings`, `ontology_information`). With the switch off the file is never read (INFO `candidate: the ontology switch is off, so the ontology is ignored`) and the bundle's `ontology` value is `null`; two ontology manifests in one release are `invalid_artifact` whatever the switch says. With the switch on the value is `{enabled, service, release_id, sha256, declared_services, findings}`, the three scalars `null` and `findings` holding one warning when no ontology is released. The `ontology` stage counts in `contracts_ms`. A CTE hides a table name only where it is in scope. `continuo_topology_contract_failures_total{stage,reason}` (stages `generate`, `validate`, `normalise`, `hash`, `ontology`; the reasons are the library's, `manifest_shape`, and `seed_header` on `validate`, and on `ontology` the library's rule names) and `continuo_topology_validation_cache_total{result}` count contract failures and the schema-check cache (up to 100,000 documents). Run tests with `docker exec topology-controller uv run pytest -v`. Start the process manually (container runs `tail -f /dev/null` by default): `docker exec -d topology-controller bash -c "cd /app && PYTHONPATH=/app/proto uv run python main.py > /tmp/mc.log 2>&1"`.

# CLI (`cli/`)
The `continuo` CLI is a standalone client of the system, intended primarily for the LLM chat to call. It is a separate Go module (`github.com/carolsimone/continuo/cli`), deliberately kept outside the parent `go.work`, and emits machine-readable JSON to stdout (human text to stderr).

Hard constraint: the CLI may consume services **only through their public gRPC interfaces**. It must never import or reuse any backend internal implementation — no `run-controller/*`, `catalog/*`, `pkg/*`, or any domain/service/adapter package. Its only dependencies are cobra, grpc, protobuf, and the generated stubs of the public `.proto` contracts vendored under `cli/proto/`. New behavior composes public RPCs client-side; it does not reach into service internals, and even at gen-time the stubs are regenerated from the vendored `.proto` copy, never from a service's source tree.

Every CLI command that starts a run, and `schedule cancel`, sends one UUID `request_id` per invocation (`CONTINUO_REQUEST_ID` when set, otherwise a fresh UUIDv4) to `run-controller`'s `run.v1.RunService`, and retries the command on `UNAVAILABLE` (not for maintenance mode) and `ABORTED` with the same id, so a lost response never starts a second run. `continuo schedule graph` reads the schedule graph from `RunService`, and its JSON carries the schedule name, its nodes (table, schema, service, node type and `dormant`) and its edges. `dormant` is true for a node continuo builds that belongs to no schedule. Only a run started by hand executes such a node, with one exception: a run whose load of a seed drops the seed's table rebuilds the dormant views and materialized views below that seed. `continuo node list` lists every node the live release builds, one that never ran included (`task_count` 0 and no `last_run_at`), each with its `node_type` and `dormant`, and `--dormant` lists only the dormant nodes.

`schedule set-cron <name> <cron> <timezone> [description]`, `schedule remove-cron <name>`, `schedule pause <name>` and `schedule resume <name>` edit a schedule's cron through `UpsertSchedule` and `DeleteSchedule`. They are mutating, send no request id, and the client retries them on a plain `UNAVAILABLE` only and returns their `ABORTED` at once: with a version above 0 it is a stale version, which sending the same request again cannot settle, and with version 0 (a first cron) it means other edits saved first on each of the server's three tries, which sending it again can settle. `set-cron`, `pause` and `resume` read the schedule first (`ListSchedules`) and send the version they read: `pause` and `resume` exit 4 (`conflict`) when another edit saved in between, and `set-cron` reads again and saves once more before it does. All four exit 7 (`maintenance`) in maintenance mode. `schedule list` emits each schedule's `cron` (empty while it has none), `version` (0 while it has none), `has_cron`, `paused`, `next_fire_at`, `model_count` and `cron_words` beside its last run.

The `run` group reads and acts on one run by id: `run show` (the run and the status, attempt, failure class and reason and node-lease wait of each task), `run graph`, `run attempts`, `run cancel`, `run rerun`, `run rebase-preview` and `run rebase`. `schedule runs` lists a schedule's completed runs, newest first. `schedule status <schedule-name>` prints the `run show` shape for the schedule's latest run, `{"run":{...},"tasks":[...]}`, and `{"run":null,"tasks":[]}` for a schedule that never ran. `run cancel`, `run rerun` and `run rebase` are mutating (the chat asks the user to approve each); `run cancel` cancels one run by id and sends no request id (a second cancel of it changes nothing). A rebase is two steps: `run rebase-preview` is read-only and prints the `release_id` of the live release with the counts of what would re-execute, and `run rebase` requires that `release_id` (its second positional, after the run id; `[with-changed-upstream]` is an optional third) and is refused with exit 4 (`conflict`) when the live release is no longer that one.

`release notices <release-id>` reads a candidate release's seed reload notices from `release-controller`'s `release.v1.ReleaseQuery` (`CONTINUO_RELEASE_CONTROLLER_ADDR`, default `localhost:50056`); it is read-only. `node full-refresh` takes a repeatable `--acknowledge <schema>.<name>`, sent as `acknowledged_dependents`: an object outside continuo that a seed's full refresh may drop. The server refuses it on anything but a seed's full refresh (exit 2, `usage`). `node contract <unique_id>`, `node contract-history <unique_id> [limit]` and `node contract-diff <unique_id> <from> <to>` read a node's contract through catalog's `GetNodeContract`, `ListNodeContractVersions` and `GetNodeContractDiff`. `<unique_id>` is `<schema>.<table>`, and all three are read-only.

LLM-friendliness is a requirement, not a nicety. The CLI is consumed primarily by an LLM, so it must be self-describing:
- Every command MUST populate `Short`, a full `Long` (purpose phrased as user intent → arguments → stdout JSON shape → the `CLIError` codes / exit codes it can return), at least one `Example`, and a clear `Usage` on every flag. Machine-readable extras go in cobra `Annotations`: `output_schema` (success-payload field names + types) and `exit_codes`.
- `continuo describe` emits a machine-readable catalog of every command, **derived** from the cobra tree (never a hand-maintained manifest). Adding a command means it appears in `describe` automatically; a test enforces that every command carries a non-empty `Long` and an `Example`, and that each `output_schema` matches the JSON the command actually emits.
- The chat sets only the flags a command lists in its `chat_flags` cobra annotation (comma-separated names of its own string or string-array flags, which a test enforces); `describe` marks them `"chat": true`, and marks a flag that may be repeated `"repeated": true`. Every other value the chat passes is a positional argument, so an optional value the chat must reach is a bracketed positional or a chat flag.

# Architecture
This repository follows an event-driven, DDD-oriented architecture using Clean Architecture boundaries.
Domain code must stay independent of infrastructure concerns. Databases, Redis, gRPC, Kubernetes, S3, framework code, and serialization details belong in adapters. Application and domain code should depend on ports/interfaces, not concrete infrastructure implementations.
Use CQRS only when it provides a clear benefit: separate write and read models, projections, asynchronous event consumers/producers, or different consistency/read requirements. Simpler services should use a straightforward DDD/application-service structure instead of unnecessary CQRS.
Handlers should be thin and delegate to application/use-case services. Use repositories and other ports to express persistence and external dependencies. Keep adapter implementations behind those ports.
Apply SOLID, clean code, repository, service-layer, and design-pattern practices pragmatically. Prefer clear, testable, explicit code over abstraction for its own sake.
Shared cross-service logic belongs in `pkg`; service-specific logic belongs inside the owning service.

## Port ownership
A port is owned by the innermost layer whose vocabulary it speaks, and adapters only *implement* ports — they never declare them. Place ports as follows, and have the `adapters/*` package implement them (with a `var _ Port = (*impl)(nil)` assertion):
- **Domain repository ports** — collection-like abstractions over an aggregate (e.g. `RunRepository`, `CancelledRunsRepository`) live in `<service>/domain/repository`.
- **Technical / application ports** — collaborators that are not domain concepts (e.g. `LogUploader`, `OutboxPublisher`, `Clock`) live in `<service>/service/ports`. The `UnitOfWork` interface stays in `<service>/service/uow`.
- **Concrete implementations** — including every `*UnitOfWork` — live in `<service>/adapters/*`.

Rules:
- The dependency arrow always runs adapter → port, never application → adapter. Code under `<service>/service/handlers` must import no `adapters/*` package; reach every collaborator through a port owned by the application/domain layer. This is enforced by the AST guard `TestServiceHandlersDoNotImportAdapters` in `pkg/streams/handler_imports_test.go` — add new services to its `handlerDirs`.
- An interface declared in an adapter package and consumed *only by other adapters* (e.g. a gRPC/Neo4j client seam) is adapter-internal and may stay there; the rule targets application→adapter inversion, not adapter-to-adapter wiring.
- Object storage is reached only through `pkg/objectstore`. The package declares one-method role interfaces (`Reader`, `Writer`, `PrefixDeleter`, `StreamWriter`, `StreamReader`, `Lister` and `Deleter`) and `ReadWriter` (`Reader` and `Writer` together). `StreamWriter.OpenWriter` opens the upload (the client's is an S3 multipart upload of 8 MiB parts) and returns an `ObjectWriter`, which must always end in `Close` (which completes the object) or `Abort` (which discards it), or the upload stays in the store: write `defer w.Abort()` right after `OpenWriter`, since `Abort` after a successful `Close` does nothing. An `adapters/*` package depends on the narrowest role it uses and never on `*objectstore.Client`, which only `main` builds (`objectstore.New(ctx, objectstore.ConfigFromS3(pkgconfig.LoadS3(v)))`: static keys when both are set, otherwise the AWS SDK's default credential chain). The adapter implements the service's own port by composing the role with the codec of its document, parses a URI it receives once with `objectstore.ParseRef` (a `Ref` value object), and translates `objectstore.ErrNotFound`, `ErrTooLarge` and `ErrInvalidRef` into the port's errors. Adapter unit tests substitute `objectstoretest.Memory`, which a contract test holds to the client's behaviour. No `<service>/domain` or `<service>/service` package imports `pkg/objectstore` or the AWS SDK (`TestNoObjectStoreImportsInDomainOrServicePackages`), and no `adapters/*` file names `objectstore.Client` (`TestAdaptersDependOnObjectStoreRoles`); both guards live in `pkg/streams/domain_json_tags_test.go`.

# Adding a remediation type
A remediation type is a YAML file, not code. It says which failures it matches, which context steps gather its evidence, which prompt the model answers and which pre-flight checks its draft must pass. The built-in files are under `agent-remediation/workflows/` and are embedded in the binary. Do these four steps, in this order:
1. Write the type file (`kind: type`, `version: 1`) as `agent-remediation/workflows/types/<name>.yaml`. Name only registered steps: `remediation-check steps` prints every one as a JSON array (`name`, `kind`, `description`, `needs`, `provides`, `stages`, `may_stand_as_gate_run`, `data_class`). Copy the closest built-in type, for example `types/dbt-parse.yaml`.
2. List it in the `types` of its flow file, `agent-remediation/workflows/flows/rejected-release.yaml`. A type no flow lists never runs, and the check warns `type "<name>" is listed by no flow`. Two listed types whose `match` can select the same failure are refused.
3. Add its fixture (`kind: fixture`, `type: <name>`) as `agent-remediation/workflows/fixtures/types/<name>.yaml`: a trigger, the repository files and the scripted model `answers` (`pass`, `fail`, `decline`). Copy `fixtures/types/dbt-parse.yaml`.
4. Run `remediation-check files agent-remediation/workflows`: from the repository, `cd agent-remediation && go run ./cmd/remediation-check files workflows`, or `go test ./cmd/remediation-check/...`, which runs the same check on the built-in files. It prints one JSON object on stdout (`files`, `errors`, `warnings`, `scenarios`) and exits 0 when there is no error and every scenario passes, 1 on an error or a failed scenario, 2 on a usage error. A warning alone does not fail it. A type that takes over a case a test pins as unhandled (today a python-csv or python-api parse failure that no type matches, pinned by `TestRunner_APythonParseFailureNoTypeMatchesIsHandedOverWithoutAModelCall` in `agent-remediation/service/runner/outcomes_test.go`) needs that test updated.

A new action, something no registered step does, is a new step and nothing else. Write it under `agent-remediation/service/steps/`, register it in `NewRegistry` in `agent-remediation/service/runner/registry.go` with its `Meta` (`Name`, `Kind`, `Description`, `Needs`, `Provides`, `Stages` and `MayStandAsGateRun`) and, when it provides a new evidence key, declare the key as a `remediation.Key<Name>` constant in `agent-remediation/domain/remediation` and add it with its Go type and data class (`code`, `logs` or `rows`) to `builtinEvidence` in `registry.go`. A file then names the step and the runner runs it. The runner fixes the stage order, so a file chooses steps and never when they run.

The file format (the keys of a flow, type and fixture file, and `version`) is a public contract: an install keeps its own files, so a change to it follows the chart's semver rules (see "Helm chart versioning"), and an existing install's files must keep loading after `helm upgrade`.

## For an install
An install keeps its own flow, type and fixture files in its own repository and gives them to the chart as `agentRemediation.workflows.files`, a map from file name to content (default `{}`), each passed as `--set-file 'agentRemediation.workflows.files.<name>\.yaml=<path>'`. The chart puts them in the ConfigMap `<release>-agent-remediation-workflows`, mounted at `/etc/continuo-workflows`, each file byte for byte, so a mounted file's revision is the revision of the file given. agent-remediation reads the folder named by `AGENT_REMEDIATION_WORKFLOWS_DIR` (default `/etc/continuo-workflows`) at startup, after the built-in files.
- A missing folder means no install files. A folder that cannot be listed stops startup. `.yaml` and `.yml` files are read, and hidden files and directories (names starting with `.`) are skipped.
- At `helm install` and `helm upgrade` the chart refuses a file whose `kind` is not `flow`, `type` or `fixture`, whose `version` is unsupported, or that holds an empty document (a `---` that only blank lines or comments follow; blank lines and comments before the first `---` are no document, as the loader reads them), naming the file. It reads directives as the loader does: a `%YAML 1.1` or `%TAG` line belongs to the document the next `---` starts, and one that no `---` follows, or `%YAML 1.2`, is refused. It refuses a top-level `kind` or `version` line written twice in one document, the only duplicate keys it sees (fromYaml keeps the last of two keys); the service and `remediation-check files` refuse every other duplicate key. With files set, it also refuses an agent-remediation `services` entry that would not show them to the service: the entry needs a `remediation-workflows` ConfigMap volume with an empty `configMap.name` (the only form that mounts the chart's ConfigMap with its digest on the pod template, so a changed file rolls the pod; any name, the chart's own included, is refused) and a `volumeMounts` entry of it, with no `subPath`, at its `AGENT_REMEDIATION_WORKFLOWS_DIR` (default `/etc/continuo-workflows`); each failure names what is wrong. With or without files, an empty-named `remediation-workflows` volume mounts that ConfigMap only while it is mounted at that folder, and the `service-repos` ConfigMap anywhere else, as a volume of any other name does.
- A file with the `kind` and `name` of a built-in replaces it whole: no list is merged. Startup logs every replacement at Warn, and a byte-identical copy is not reported. An install file at the path of a built-in file (possible only in a folder with subdirectories, never in the chart's flat ConfigMap) is refused, naming both, while a built-in flow or type of that file stays loaded (no install file, at that path or another, replaces it), so a path names one loaded file; the service and `remediation-check` refuse it. A fixture at the path of a built-in file whose flow, type or fixture stays loaded, or a flow or type at the path of a built-in fixture that stays loaded, is refused by `remediation-check` only (`workflowfile.CheckInstallPaths`), since the service never reads fixtures.
- `based_on: <name>@<revision>` in a flow or type file makes startup warn when the built-in of that name and kind has moved since. The revision is the first 12 hex characters of the sha256 of the bytes of the built-in file in the continuo repository at the tag of the version the install runs (`git show v<version>:agent-remediation/workflows/<path> | sha256sum | cut -c1-12`); the startup warning also prints the built-in's current revision (`based on <name>@<revision>, which is now @<revision>`). A `based_on` that is not `<name>@<revision>` is refused.
- Heal triggers run only the flow named `rejected-release`. An install lists a new type by replacing that flow file: same name, the whole file, with the type added to `types`. A flow of another name is loaded, validated and played by `remediation-check` as itself (each of its scenarios runs a remediation that follows it, so fixtures copied from `rejected-release` fail the scenarios it cannot handle), but no heal trigger runs it, and startup and `remediation-check` warn `flow <name>: no heal trigger runs it`. A type is played in `rejected-release` when it lists the type, else in the first flow by name that lists it.
- An install type that replaces a built-in type and ships no fixture is played against the built-in's fixture of that name. A type that is new to the install needs its own fixture, or `remediation-check files` fails it (the service still starts, since it never reads fixtures). A replaced flow is still played against the built-in flow fixtures, and an install fixture of the same flow and scenario replaces one.
- The built-in fixture of a built-in type that no loaded flow lists (a replaced `rejected-release` drops it) is left out, and `remediation-check files` warns `<file>: skipped, no loaded flow lists type <name>`. A replaced flow whose types or cross-cluster checks differ can fail a built-in type or flow fixture (a shared-upstream member falls back to the type the flow dropped): an install fixture of the same type, or of the same flow and scenario, replaces it. An install fixture that nothing plays fails: one of a type no flow lists, or of a flow no file defines.
- Remove or roll back an install type only when no remediation of that type is in flight: a cluster whose type the loaded files do not define fails its `plan` step on every drive, so after five failures the remediation ends as a system failure whose reason names the type, and redriving its dead letter (`continuo dlq`) once the file is back resumes it.
- In the install's CI, run `remediation-check files <dir>`, with `<dir>` the folder of its files, in the agent-remediation image of the continuo version the install runs (`/usr/local/bin/remediation-check`; the chart README's "Remediation files" gives the `docker run` command). The exit codes are the ones in step 4. A message names a file by its path under `<dir>`, and a path under `flows/`, `types/` or `fixtures/` that `<dir>` does not hold is a built-in file.

# Stream and consumer-group names
Every Redis stream and consumer group is declared in `pkg/streams/contract.yaml`. A Go generator emits `pkg/streams/streams.gen.go` (`streams.TaskDispatchV1`, `streams.RunCancelledV1`, `streams.ExecutionControllerTaskDispatch`, etc.) and `topology-controller/streams_contract.py` for Python.

The same file's `vocabularies:` block declares the closed value sets several services agree on: `parse_failure_kind`, `reject_reason`, `validation_op`, `handover_reason`, `approver_source`, `contract_family`, `remediation_source`, `dead_letter_kind`, `node_runtime`, `node_type`, `run_status`, `task_status`, `operation`, `attempt_status`, `failure_class` and `failure_reason`. The same generator run emits those into the **shared domain packages**, not the transport ones: `pkg/domain/model/vocabulary.gen.go` (one type per vocabulary, such as `model.ParseFailureKind`, `model.RejectReason`, `model.ValidationOp` and `model.HandoverReason`, each with `IsValid()`, and `Healable()` where the contract marks a value `healable`), `topology-controller/domain/contract_vocabulary.py` and `ui/src/server/generated/vocabulary.gen.ts`. Domain, application and adapter code names a contract value from there.

`pkg/streams` and `streams_contract` hold stream and consumer-group names only, and **no `*/domain` package imports either** — enforced by `TestDomainPackagesDoNotImportStreams` in `pkg/streams/domain_imports_test.go` (Go) and `topology-controller/tests/test_domain_imports_no_streams_contract.py` (Python).

Rules:
- Never inline a versioned stream name (`"task.dispatch:v1"`) or a service-prefixed consumer-group name in Go, Python, or tests. Always reference the constant from `pkg/streams` (Go) or `streams_contract` (Python).
- This applies to production code, integration tests, unit-test fixtures, and adapter bindings (`message_processing.stream_name` values must come from the constant, not a local `const fooStreamName = "foo:v1"`).
- The AST wiring detector in `pkg/streams/wiring_test.go` rejects hardcoded versioned-stream literals in service `main.go` files; new occurrences in handlers, bindings, or tests should be removed for the same reason.
- A consumer group is named `<consuming service>-<purpose>`, so the group a stream shows in `XINFO GROUPS` names the service that reads through it (`run-controller-task-status-updated`, `execution-controller-task-dispatch`). `TestConsumerGroupsStartWithTheirServiceName` in `pkg/streams` fails a group in `contract.yaml` that does not start with its `service:` value followed by `-`.
- Adding a new stream, group, or vocabulary value means editing `pkg/streams/contract.yaml`, regenerating (`go generate ./pkg/streams/...`), and committing the regenerated files. CI's `go generate && git diff --exit-code` check enforces freshness.
- The AST guard `TestLifecycleGoNeverWrapsAServerStart` in `pkg/streams/lifecycle_wiring_test.go` discovers every service's `main.go` by glob and fails if a blocking-server method (`Start`/`Serve`/`ListenAndServe`/`ListenAndServeTLS`/`Run`) is called, inside a `lifecycleManager.Go(...)` tracked goroutine, on a receiver that is also stopped by a `RegisterShutdownHandler(...)` closure in the same file — that combination deadlocks the drain step of graceful shutdown, since the server can only return after the shutdown handler that follows the drain runs.

# Install-level configuration must reach the code
A property of the operator's environment — warehouse engine, region, auth mode, timezone, an external component's version — is declared once in `deploy/continuo/values.yaml` and must travel from there to every process that acts on it. Two halves of the same bug, both of which have shipped here:

- **A hardcoded literal.** An environment-dependent value baked into code (`dialect="postgres"`, a region, a port, a schema name) works for whoever wrote it and is wrong for every other install.
- **A declared value that stops at the chart.** A key that only feeds a Helm template — picking an image, naming a Secret — makes the system *look* configurable while every service still runs the author's default. This is the harder half to see: grepping the key name finds `values.yaml`, and you conclude it is wired.

Rules:
- A values key that describes the user's environment must reach the services that act on it — normally as a key on the shared ConfigMap in `templates/configmap.yaml`, mirrored into `docker-compose.yml` and any other deployment path. If it is genuinely install-time-only (image selection, Secret naming), that is fine, but say so in the values comment so the next reader need not re-derive it.
- Services **fail closed** at startup on a value they cannot honour, rather than degrading to a default mid-operation. `_helpers.tpl` already fails an install on an unsupported `validation.engine`; the service must refuse to boot rather than emit another engine's output.
- Where the same set of allowed values is enumerated in two places, pin them to each other with a test (`test_supported_engines_match_the_chart` in `topology-controller/tests/test_config.py`), so the chart cannot start accepting a value the code cannot honour.
- When you remove a hardcoded literal, sweep every site of that concept rather than only the one that was flagged, and separate the **read** sites from the **write/generate** sites. The generate site is usually the real defect: its output leaves the process as an artifact another system executes, so a wrong value there surfaces far from its cause. `topology-controller/tests/test_dialect_guard.py` is the forcing function for the SQL-dialect case; add the equivalent guard when you fix a new instance of this class.

# Architecture documentation
The architecture pack under `docs/arch/` is part of the working agreement for this repository.
Before completing any task that changes service behavior, interfaces, storage ownership, Redis flows, gRPC interactions, Kubernetes behavior, or S3 usage, the LLM must review and update the relevant files in `docs/arch/`.
Do not consider a task complete until the architecture documentation has been reconciled with the implemented code changes.

**Arch docs describe the system's current working only — present tense, self-contained.** They are held to the same standard as code comments (see the IMPORTANT rules below): a new reader with no prior knowledge must understand what the system does today from the text alone. So:
- No references to past PRs, past edits, migrations-as-history, or a change ("previously", "used to", "was renamed from", "after the cutover", "we removed"). State what is true now. Describing a value that is *currently* absent is fine when it reads as current state ("the projection stores only X"), not as a change narrative.
- No future/roadmap framing ("will be added later", "planned", "TODO"). Habitual/runtime "will" ("the reconciler emits once a release answers") is fine.
- No cross-references that only resolve relative to an edit or another section's numbering — e.g. citing "Step 3a" outside the numbered flow that defines it. Name the mechanism (the function, the field) instead.
- Deprecated/removed features are simply absent, not documented as history.

**Mermaid sequence diagrams never carry a raw `;` or `#` in their text.** In a `sequenceDiagram`, `;` ends a statement like a newline does, so a `;` in a message, a `Note` or an `alt`/`else`/`opt`/`loop` label is a parse error and the whole diagram fails to render; a `#` there drops the rest of the line without an error. Separate clauses with `,` or `<br/>`. A quoted string that must keep one writes it as Mermaid's entity code: `#59;` for `;`, `#35;` for `#`.

Services should be Go based service, find `Dockerfile.dev` in the service folders if you need to know how to build them.
The exception is `topology-controller`, which is Python 3.14 and uses uv for dependency management.
All the other services should, more or less, use a similar stack but with different dependencies.
Remove any dependency that is not needed.

# Retired names
`retired-names.yaml` at the repository root lists the names the glossary replaced. `TestNoRetiredNames` in `pkg/deploycheck` (run by `make guards`, so by CI on every pull request) fails when a tracked file holds one: code, UI copy, contracts, generated files, migrations or docs. Each failure reads `<file>:<line>: "<old name>" is a retired name; use "<glossary word>"`. Three places keep old names on purpose and are not checked: the `_Avoid_:` lines of every `GLOSSARY.md`, the released sections (`## [x.y.z]`, `## x.y.z`) of `deploy/continuo/CHANGELOG.md` and `docs/release-notes.md`, and the list itself.

A rename pull request adds the old names of its term group to the list, in the same pull request that removes them from the code, so a renamed term cannot come back:
1. Add one entry per old name under `names`: `pattern` (a Go regular expression the guard wraps in word boundaries, so `foo` does not match `foobar`, `foo_bar` or `fooBar`; case-sensitive unless it starts with `(?i)`), `use` (the glossary word) and, when the name is retired only in some places, `paths` (directories, files or globs from the repository root; `*` and `?` stay within one path segment, `**` crosses segments). The file's header shows an example entry. Because of the word boundaries, the pattern lists the name's code forms itself, for example `attempts?|attempt_\w+|[aA]ttempt[A-Z]\w*` for `attempt`, `attempt_id`, `attemptCount` and `AttemptStatus`, and starts and ends with a letter, digit or `_`.
2. Run `cd pkg && go test ./deploycheck/ -run TestNoRetiredNames` and rename every occurrence it lists. A word that is right in its own context (a Kubernetes Job, a dbt snapshot, a library's own name) needs a pattern or `paths` that leave it out, not an exemption.

The guard refuses a list it cannot honour: an unknown key, an entry with no `pattern` or `use`, a pattern that does not compile or matches the empty string, and a path that names no tracked file.

# Helm chart versioning (`deploy/continuo/`)
`release.yml` locks the chart's `version` and `appVersion` together — one `vX.Y.Z` git tag stamps both identically and retags every service image to match, so there is no chart-vs-app compatibility matrix to track. The only thing chart versioning has to protect is: **does an unmodified existing user's `values.yaml`/overrides still produce a working install after `helm upgrade` to the new version?**

Whenever a PR changes `deploy/continuo/values.yaml`, `values.schema.json`, `Chart.yaml`, or `templates/**`:
- **Update `values.schema.json` to match.** `additionalProperties: false` is set throughout on purpose — adding, renaming, or removing a values key without updating the schema fails `helm lint` (`scripts/install-test/lint.sh`), which is the intended forcing function.
- **Add an entry under `## [Unreleased]`** in `deploy/continuo/CHANGELOG.md` (Added/Changed/Removed/Breaking, [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format). CI (`scripts/install-test/changelog-check.sh`, wired into `install-test.yml`) fails a PR that touches the chart's user-facing surface without this, and a PR whose diff adds a line under an already released `## [x.y.z]` section — which a merge of main after a release cut does without a conflict — unless the diff adds that version's heading (the release cut itself). It also fails a PR that moves topology-controller's `continuo-contracts` pin in `topology-controller/pyproject.toml` without a CHANGELOG line naming `continuo-contracts <new version>`.
- **Decide the semver bump** the change implies, scoped to the values contract rather than internal service APIs:
  - PATCH — template/default fixes, no values schema change.
  - MINOR — new values added with safe defaults; existing overrides keep working unmodified.
  - MAJOR/Breaking — anything that breaks an unmodified existing values file on upgrade: a renamed/removed key, a previously-optional value becoming required, an immutable field changing (Service selector, PVC size, StatefulSet volumeClaimTemplates), or dropping support for an older `kubeVersion`.
- **If a value becomes newly required**, add an `{{ if .Release.IsUpgrade }}` warning to `templates/NOTES.txt` telling operators what to set — the changelog is easy to miss, but NOTES.txt is what actually prints at `helm upgrade` time.
- Validate with `bash scripts/install-test/lint.sh` (helm lint + template + kube-linter across all four values topologies) before pushing.

Release order: merge the release cut (the PR that adds `## [X.Y.Z]` to `deploy/continuo/CHANGELOG.md`), then push the `vX.Y.Z` tag on that commit. The tag can go at once: the cut's own push publishes its `:<sha>` images, since `deploy/**` is in `deploy.yml`'s release filter, and `release.yml` waits for that run (`scripts/release/wait-for-image-publish.sh`) before `scripts/release/retag-images.sh` checks that every image exists.

After a release: once `release.yml` has succeeded for `vX.Y.Z` and the docs-pin PR (the one pinning this repository's install guides to `X.Y.Z` and adding its release notes) has merged, run `scripts/release/open-site-bump-pr.sh X.Y.Z`. It opens the pull request in `carolsimone/continuo-site` that moves the public site's quickstart `chartVersion` to `X.Y.Z`; nothing else bumps that pin. It runs with your own `gh` login, and `release.yml` does not call it, because it needs push access to that second repository.

# Pull request titles and labels
Every pull request title is a Conventional Commit title: `<type>[(<scope>)][!]: <summary>`, for example `fix(run-controller): stop double-dispatching a retried task` or `feat(cli)!: rename node trigger to node run`. The repository squash-merges, so the title becomes the commit message on `main`. The `pr-title` check (`.github/workflows/pr-title.yml`, backed by `scripts/pr-title-type.sh`) fails any other title; a `Revert "…"` title that GitHub generates is accepted. `<type>` is one of the prefixes below, `<scope>` is optional and lowercase (`run-controller`, `ui,cli`), and `!` marks a breaking change.

The `pr-labels` workflow (`.github/workflows/pr-labels.yml`) labels every pull request except dependabot's. Labels are never set by hand: edit the title and the workflow rewrites the type labels. Every label name is lowercase.
- **Type, exactly one, from the prefix:**

  | Prefix | Label |
  |---|---|
  | `feat` | `enhancement` |
  | `fix` | `bug` |
  | `refactor` | `refactoring` |
  | `docs` | `documentation` |
  | `perf` | `performance` |
  | `ci` | `ci/cd` |
  | `test` | `test` |
  | `chore`, `build` | `chore` |
  | `security` | `security` |

  `!` adds `breaking-change`.
- **Area, one or more:** `area/<name>` for each of `run-controller`, `catalog`, `execution-controller`, `release-controller`, `remediation`, `agent-remediation`, `agent-chat`, `topology-controller`, `dead-letter-controller`, `egress-proxy`, `ui`, `cli`, `pkg`, `deploy`, `db`, `dbt` whose directory holds a changed file that defines behaviour. Tests, Markdown and generated code (`*.gen.go`, `*.pb.go`, `*_pb2*.py`, the streams contract bindings) do not count, so a pull request that only regenerates stubs or adds a test does not claim the area. `area/e2e` marks a pull request whose every changed file is under `tests/`, and `area/docs` one whose every changed file is documentation. A workflow or script change carries no area; its type label says what it is. The rules are in `.github/labeler.yml`.
- **Left alone:** `p1`–`p3`, `benchmark` and every other label are set by hand and never changed by the workflow.

A new service needs its `area/<name>` label created in the repository and its rule added to `.github/labeler.yml`.

# How to run it
Everything needs to run against docker images within my host machine. I use MacOS M4 and colima to be precise.
All should be added to the `docker-compose.yml` file at the root of the project.

**Basic:**
* Build the base image first: `DOCKER_BUILDKIT=1 docker build -t continuo-base:latest -f Dockerfile.base .`
* Run `bash scripts/setup.sh`: this creates a `kind` cluster, builds all service images via `docker compose build`,
  and dumps the kubeconfig into the service directories that need it for Kubernetes API calls.
* You need to access the service/image using docker. Once you are in the container, you can run all the
  `tests`. Tests must pass successfully.
* Abide by the Go coding standards.
* Dead code fails CI twice over: golangci-lint's `unused` catches unexported code, `make guards` runs `scripts/check-dead-go.sh` (`deadcode`: functions no service `main` reaches, exported ones included; intentional exceptions go in `scripts/deadcode.allow`) and `npm run knip` in `ui/` (production mode, config in `ui/knip.jsonc`). Delete the code rather than allowlist it; a test that is the only caller does not make code live.
* `pkg` folder should contain all the logic shared between services.

**Running the e2e test:**
Please read: `tests/e2e/README.md`.

**Database schema in integration tests:**
Integration tests run against the schema the Flyway migrations in `db/migration/` built (`make test-deps-up` applies them). A test never issues DDL, never replays migrations, and never creates test-only tables or databases; it cleans up by `TRUNCATE` or `DELETE` of the rows it owns. A test-only schema drifts from production, and a `DROP` on a shared database breaks every other suite that uses it. A test whose tables are missing fails with a message to run the migrations, rather than rebuilding them.

catalog's Neo4j schema lives in code (`InitSchema`). A catalog test that needs Neo4j DDL, such as the startup migration's tests, runs against its own throwaway Neo4j started with testcontainers (`ownNeo4j` in `catalog/adapters/neo4j`). Every other catalog test runs against the docker-compose Neo4j, on the schema `InitSchema` builds.
