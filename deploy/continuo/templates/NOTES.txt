{{- if .Release.IsUpgrade }}

UPGRADE NOTES
  This chart does not yet auto-detect which new/changed values apply to your
  release — check the changelog for anything between your previous version
  and {{ .Chart.Version }} before assuming this upgrade is a no-op:

    https://github.com/carolsimone/continuo/blob/main/deploy/continuo/CHANGELOG.md

  A "Breaking" entry means a value's meaning or requirement changed; a
  "Changed"/"Added" entry may still need a new value set to enable a feature.
  If this upgrade already failed, re-run with --dry-run to see the exact
  rendering/validation error before retrying for real.

  From continuo 0.21.x or earlier: this version computes every node's content_hash
  anew. Freeze producer merges, then release each service once (Python services
  rebuilt on continuo-python-runtime 0.12.0 first) with "bootstrap": true and
  "rebaseline": true, so nothing is validated or reloaded; the steps are in
  deploy/README.md, "Re-baseline after a fingerprint change".
  The default validation image is now v0.12.0.
  An overridden dbt-commands file whose run commands parse with other --vars,
  --target, --profile, --profiles-dir or --project-dir values than its compile
  command stops execution-controller from starting.

  A validation.imageTag below v0.12.0 fails the render: that runner has no
  seed preflight. Re-pin it to v0.12.0 or later, or drop the override to
  track the chart's default.

  A values file that overrides the whole services list gets neither
  release-controller's grpcPort and RELEASE_CONTROLLER_GRPC_PORT nor
  agent-chat's CONTINUO_RELEASE_CONTROLLER_ADDR: copy them from the chart's
  values.yaml, or continuo release notices cannot reach release-controller.

  From continuo 0.11.x or earlier: the run-controller service now plans every
  run. When it first starts on this version, it cancels each run still pending
  or running that it did not plan (cancelled by "system", reason "the run's
  tasks were not planned by run-controller, so it cannot continue"). Their
  queued tasks never start, and the results of Jobs already running are
  ignored. Such a run cannot be rerun: trigger its schedule again. To keep
  in-flight runs, upgrade with none active: turn maintenance on, wait until no
  run is pending or running, upgrade, then turn maintenance off.

  Release topologies live in object storage (tenants/<tenant>/topologies/ in
  your bucket).
  With an external bucket (s3.*), grant topology-controller write access and
  release-controller read/write/delete access to tenants/, and keep any
  lifecycle expiry rule off that prefix.
  catalog and run-controller also read tenants/ (read access with an
  external bucket).
{{- if .Values.validation.imageTag }}

  BREAKING — validation.imageTag is set on this release, and the validation
  image now ships from a DIFFERENT repository. Validation runs the merged
  {{ include "continuo.validation.image" . }}
  image; your pinned tag is composed into that new repository verbatim, so a
  tag or digest carried over from the retired continuo-validation-<engine>
  repository resolves to nothing and every validation Job fails ErrImagePull.
  Either drop the override to track the chart default, or re-pin against
  ghcr.io/carolsimone/continuo-python-runtime-{{ .Values.validation.engine | default "postgres" }}
  (digests are repository-scoped and do not carry over).
{{- end }}

  catalog now reads object storage to record node code-version history, so
  it needs S3 to be reachable and authenticated. The chart supplies the
  credentials for you — they no longer come from the `services` list, so an older
  copy of values.yaml still works — but two things are yours to check:
    * If you run a NetworkPolicy of your own (not this chart's), allow
      catalog egress to your object store.
    * If you set s3.* for an external bucket, catalog now needs read access
      to the code-bundles/ prefix.
  Until it can read that prefix, promotions still succeed and runs are
  unaffected: only code-version history is skipped, and it catches up on the
  next release once access is granted.

  The validation image ({{ include "continuo.validation.image" $ }}) is an
  externally released image, pinned by validation.imageTag independently of
  this chart's appVersion. If you mirror continuo images into a private
  registry (global.imageRegistry/global.imageRepositoryPrefix), mirror this
  ref too — an install can come up healthy and only fail later, at the next
  release promotion, with a validation-pod ErrImagePull.
{{- end }}

{{- if .Release.IsUpgrade }}

Every service now runs under its own ServiceAccount, named after it, not the namespace's default one.
Image pull secrets, RoleBindings and cloud roles bound to the default ServiceAccount no longer apply:
set imagePullSecrets (and services[].serviceAccount.annotations for cloud roles) in your values.

Every Redis key now lives under the prefix `continuo:` (streams, ui sessions,
agent-chat's rate-limit keys, agent-remediation's LLM cache keys). Consumer
group names do not change. The streams-init step creates each stream and
consumer group under that prefix. With redis.enabled=false it is a pre-upgrade
hook Job that runs before the services roll. With the bundled Redis it is a Job
of the release, which the services wait for (up to five minutes). The ui keeps
its sessions under continuo:uisession:, so every ui user signs in once more
after this upgrade, and agent-chat's rate-limit counters and agent-remediation's
LLM cache start empty.
streams-init needs a Redis login that may create streams (XGROUP CREATE with
MKSTREAM). If yours may not, have the Redis owner create the streams by running
/streams-init from the dead-letter-controller image with a login that may, and
set redisInit.createStreams=false. Until the streams exist, consumers wait for
their groups and producers retry.
{{- end }}

entry catalog and delete POSTGRES_DB and POSTGRES_PASSWORD from it.
With the bundled Postgres a POSTGRES_DB left there gives catalog's pod an init

{{- if .Release.IsUpgrade }}

BREAKING: upgrade through continuo 0.10.0 first. This release drops
release-controller's inline topology columns, and its database migration
refuses to run until release-controller 0.10.0 has started once and
moved their contents into object storage. From an older release, upgrade to
0.10.0, wait until release-controller is Ready, then upgrade to this
release. Upgrade with no release in flight (maintenance on, the active release
finished). release-controller refuses to start until that migration has
applied; if it keeps exiting with a message naming the db-init-migrate Job,
the migration refused: upgrade to 0.10.0 first.

BREAKING (service renames): the "ui-service" service is now "ui". If your
values override services[].name entries, update them before upgrading.
Also, if you use ingress.tls.enabled=true with the default TLS secret name,
it changed from "ui-service-tls" to "ui-tls"; rename/recreate the Secret or
set ingress.tls.secretName explicitly, or TLS will break.

BREAKING: "agent-runner" is now "agent-chat". Before upgrading, rename its
database: ALTER DATABASE continuo_agent RENAME TO continuo_agent_chat;
otherwise a fresh empty database is created and chat state is stranded. If
your values override global.agentRunnerGrpcAddr, rename it to
global.agentChatGrpcAddr.

BREAKING: "remediation-agent" is now "agent-remediation". Before upgrading,
rename its database: ALTER DATABASE continuo_remediation_agent RENAME TO
continuo_agent_remediation; after upgrading, delete the drained consumer
group: XGROUP DESTROY remediation.requested:v1
remediation-agent-remediation-requested.

BREAKING: "manifest-controller" is now "topology-controller". It has no
database of its own, so no rename is needed there. After upgrading, delete
the drained consumer group: XGROUP DESTROY release.requested:v1
manifest-controller-release-requested.

  BREAKING — if your values override agentRemediation.env.SHADOW_VERIFY_TIMEOUT or
  SHADOW_VERIFY_POLL_INTERVAL, rename them to VERIFICATION_TIMEOUT and
  VERIFICATION_POLL_INTERVAL; the old keys are no longer read.

BREAKING: "executor-controller" and "k8s-controller" are now one service,
"execution-controller", with its own database continuo_execution (created and
migrated by this upgrade). Nothing is copied from continuo_executor or
continuo_k8s, so upgrade only when nothing is in flight: stop the old services
and let every run, release and queued retry finish first. After the new pod is
Ready and a run has completed, drop the old databases yourself: DROP DATABASE
continuo_executor; DROP DATABASE continuo_k8s;
This chart never drops a database. If your values override services[].name
entries for either old service, replace them with one execution-controller
entry (see values.yaml). That merge renames no consumer group; do not delete any
for it.

BREAKING: "state" is now "run-controller": the image continuo-run-controller,
the Deployment, Service and NetworkPolicy, the address run-controller:50051 and
the database continuo_run_controller. Before upgrading, rename its database:
ALTER DATABASE continuo_state RENAME TO continuo_run_controller; otherwise a
fresh empty database is created and the run history is stranded. If your
values set global.stateGrpcAddr, rename it to global.runControllerGrpcAddr; if
they override services[].name entries, name the entry of that service
run-controller with POSTGRES_DB continuo_run_controller. The consumer groups
follow their services' names (state-task-status-updated,
state-release-promoted and the nine executor-* groups of execution-controller
become run-controller-* and execution-controller-*). In this order, as the
CHANGELOG's entry for this version describes in full: redrive the open dead
letters of those groups and let the consumers finish them (after the upgrade a
dead letter of an old group cannot be redriven); scale state and
execution-controller to 0 with an empty pending list on every old group; take a
pg_dump of continuo_state; and only then create each new group at its old
group's last-delivered id; rename the database; upgrade; destroy the old groups.
{{- end }}

BREAKING: agent-chat and agent-remediation reach the outside world only
through egress-proxy, which admits a connection only to a host and port on its
allowlist. An install upgraded from a chart that left their outbound traffic
open fails every call to a destination that is not on the list.
{{- if eq (include "continuo.egress.proxyEnabled" .) "true" }}
The allowlist holds your LLM provider (llm.provider / llm.baseUrl), GitHub,
with an external bucket your S3 endpoint, and egress.allowedDomains and
egress.privateDomains:
  kubectl -n {{ .Release.Namespace }} get configmap {{ include "continuo.egressProxy.configMapName" . }} -o yaml
{{- else }}
Every destination of this install is an IP address, and egress.allowedDomains
and egress.privateDomains are empty, so the allowlist is empty: no
egress-proxy object renders and the agents get no proxy variable. They reach
those addresses directly.
{{- if .Values.networkPolicy.enabled }} Their NetworkPolicy still drops every
connection except DNS, the pods of this namespace, an external Postgres or
Redis on its configured port, the pods of another namespace on the port of each
in-cluster address the agents are given there, and those direct destinations.
{{- end }}
{{- end }}
If the agents reach anything else:
  * another host name: add it to egress.allowedDomains (egress.privateDomains
    when it resolves to a private address);

    any other address reached without the proxy: add the address to
    egress.directDestinations ({cidr, ports}). An IP address in
    externalDatabase.host, externalRedis.host, a URL or address the agents

  * to keep their outbound traffic open: set egress.enabled=false.
